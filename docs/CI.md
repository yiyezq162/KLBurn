# 源码检查与发行验收

`.github/workflows/check.yml` 在 main 推送、Pull Request 和手动触发时运行源码回归。
它不是 ISO 发布流水线，不构建或发布 ISO，也不以源码测试成功代替硬件验收。

## 运行环境

- 源码回归使用 x86_64 Ubuntu 24.04、Bash、Python 3、shellcheck 和 iproute2。
- 默认使用一次性 GitHub 托管环境，fork 无需维护者的 Runner。
  可信分支可设置仓库变量 `CI_RUNNER=self-hosted`，并通过
  `CI_RUNNER_LABELS` 的 JSON 字符串数组指定自己的专用 Runner 标签。
  基础工作流将 Pull Request 分到 GitHub 托管环境，不受上述变量影响；
  这不限制 Pull Request 修改 YAML，安全边界见下节。
- 不向不可信 Pull Request 提供私有回归样本、凭据或构建机管理权限。
- ISO 的 root、chroot、loop/mount 和 KVM 操作在符合条件的独立后端执行，
  不在普通容器 Runner 中执行；普通开发不需要重新注册维护者的 Runner。

## 公开仓库与自托管 Runner

工作流默认把 Pull Request 分到 GitHub 托管环境，是调度约定，不是服务器端隔离。
Pull Request 可以修改工作流内容；仅检查基础分支 YAML、把 token 权限设成只读，
或不注入 secrets，都不能证明自托管主机及其网络不受影响。

本项目的公开流程不以这类 YAML 约定作为自托管安全放行条件。公开前应由所有者
确认退役此仓库直接绑定的自托管 Runner 注册，或提供可核验的服务器端可信工作流
隔离。个人账户下的仓库级 Runner 不应被默认视为已有这类隔离。
`CI_RUNNER=self-hosted` 的使用前提是私有、受控环境或已经证明有效的隔离边界，
不是给公开 fork 绕过 GitHub 托管环境的入口。

退役某个仓库的注册不等于删除构建虚拟机。不得为此盲目删除 Runner、停止 NAS
共享服务、改动其他项目或重新注册执行器；应先核对准确归属并取得相应操作授权。
独立构建机中的完整回归和私有样本仍需保留。默认完整入口缺样本时照实失败，
不能通过公开客户原始数据、删除回放守卫或把缺失覆盖记为 PASS 来换取绿灯。

## 真实回放样本与测试分母

`tests/run-all.sh` 默认完整范围，同时包含合成输入测试和真实传感器/电源样本回放守卫。
后者要求调用者有权使用的 `test_out/` 输入，包含传感器读数及未接交流电的真实
观察。没有这些资料时检查会明确失败；不能伪造输入、删除守卫或把空转计作通过。
公开测试夹具保留解析所需的字段形状，但设备序列号、资产标识、UUID 和网卡地址
使用明确虚构的标识或协议保留示例地址，不代表真实客户设备。缺失、坏值及重复序列号
的判定用例仍然保留。它们与 `test_out/` 中有权使用的真实回放输入是不同的证据来源，
不能把合成夹具算作真实回放或真机验收。源码中不包含客户原始报告。
样本不得作为公共 Actions artifact 上传。

GitHub 托管 CI 显式运行 `./tests/run-all.sh --public`：执行公开源码测试，但不读取
`test_out/` 中的真实传感器/电源回放输入，并将该回放组标为 **NOT_RUN**。
两项覆盖守卫和依赖样本数量的回放断言不计入公开范围的 PASS，不能给未知样本数
编造总分母。`test-hw-checks.sh --public` 同样仅用于这个明确的公开范围。
无参数入口仍要求两项覆盖守卫通过；未知参数报错，不根据环境变量或样本缺失自动降级。
发行脚本与定制构建继续调用无参数的完整入口，不能用公开 CI 绿灯放行 ISO。

`test-ci-scopes.py` 在不含私有资料的独立源码副本中验证：默认入口缺样本必须失败、
公开范围不读取私有样本目录、非法参数被拒绝，并逐一删除两条覆盖守卫进行定向变异验证。
这些是测试范围契约检查，不算真实回放或真机验收，也不替代发行所需的完整变异测试。

公开源码在无私有样本的环境中运行，不等于能够复现维护者的完整回放分母。
必须分别记录实际 PASS、FAIL、SKIP/NOT_RUN、样本覆盖和执行环境。
回放历史样本不是新一轮真机验收；非 root 源码回归也不包含 root 磁盘排除检查。

可信自托管流程只在自己拥有的任务工作区复制样本，退出时清理该次任务的副本，
不修改原始资料。构建工具使用外部用户自己的后端、离线组件和样本，
不提供对维护者环境的访问。
自托管维护者将原始样本的绝对目录保存为仓库 secret `CI_FIXTURE_DIR`；
源码不包含其路径，Pull Request 不注入该值。缺失配置或样本仍然失败，
不得将不含真实回放的托管任务结果当成完整回归通过。

## 日志与 artifact

源码工作流按 run/attempt 保存检查日志，并在上传失败时作一次有界重试。
测试失败仍然失败；上传成功不是测试成功。没有完成上传的证据不能写成已交付。

公开前必须单独审核旧 Actions 日志/artifact、Release 附件和发布说明。
不把包含内部路径、客户资料或运维记录的 manifest 直接转换为公共附件。
公开下载元数据使用 [发布说明](publication.md) 中的受限生成流程。

## 成对发行验收

完整规则见 [构建说明](building.md)，顺序为：源码检查（需要时变异测试）→
提交并保持源码干净 → 同一 commit 串行构建 full/mem → 两版固件/依赖与
QEMU 验收 → full 完整写盘验收 → 实际截图和报告检查 → annotated tag。

QEMU 写盘验收使用隔离测试镜像，不能称作物理服务器、GPU、RAID 或真实内存条
验收。未执行项保留 NOT_RUN。失败重跑保留首次失败，不覆盖历史 tag 或资产。

版本变化见 [CHANGELOG](../CHANGELOG.md)。内部构建收据保存版本、commit、
两版文件大小及 SHA256、各套件分母和限制，但不自动公开。
另见 [第三方分发边界](third-party.md)；软件测试通过不证明分发权利。
