## 一、破坏性 fio 真写盘的端到端（最高优先级）

### 为什么

「fio 不会把启动 U 盘写穿」是这个项目**最危险的一条路径**
（[§8.2](architecture.md#82-裸盘写入的排除规则storagesh)）——
一旦退化，测试盘当场报废、历史报告全丢。

现在守它的只有 `tests/test-disk-exclusion.sh`：用 loop + dm-linear 搭出和
Ventoy 同构的设备链。那是**构造出来的**，而且它只验反查逻辑，
**没有任何一次是真的让 fio 跑起来写盘的**。

`e2e-qemu.sh --stage full` 里这一项始终是 SKIP —— 自动化里不能瞎确认破坏性写入。
所以这条路至今一次都没被端到端走过。

### 怎么做（机制已验证）

难点是"什么时候按键"。硬盘确认有两道提示，出现的时刻不固定
（在 `collect_all` 之后，而采集耗时随机器变化），按时间盲发不可接受 ——
**按错方向就是真擦盘**。

**可行的锚点：在宿主机上轮询 usb.img。** 虚拟机往 exFAT 分区写的 `klburn.log`
在宿主机看来就是 `usb.img` 里的一段字节，跑着的时候就能 grep 到：

```bash
grep -a 'verify_dmesg_boot' "$WORK/usb.img"   # 实测 2.5GB 镜像耗时 0.4 秒
```

`OK verify_dmesg_boot` 是 `collect_all()` 打的**最后一条**日志，
紧接着就是 `confirm_disk_write()`。所以：

1. 轮询到 `verify_dmesg_boot` 出现 → 等 2~3 秒 → sendkey 打出 `y` `e` `s` + `ret`
2. 第二道是最终警告面板（按 `y` 才真的开始，60 秒超时）——
   给它找一个新锚点，或者退而求其次用"第一道之后固定延时"
   （这道的时间窗是确定的，风险小得多）
3. 之后照常等 fio 跑完

> 第 2 步如果找不到干净的锚点，可以考虑在 `stress_disk()` 开头加一行
> `log` 输出当锚点 —— 那是产品代码里一行日志，不是"为测试开后门"。

### 怎么算做完

跑完之后同时满足：

- 两块空白盘（`spare*.img`）的内容**变了**（真的被 fio 写过）——
  比 md5 或看文件里非零字节
- `usb.img` 第 4 分区**还能挂上**，而且**上一轮的报告还在**
  （证明没被写穿）
- `results.jsonl` 里 `stress_disk` 是 PASS，不是 SKIP

再加一条反向断言：把 `live_media_disks()` 改坏（`mutate.sh` 里加一条变异），
这个场景必须跑红。

### 预估

半天。大头在调按键时序，不在写断言。

## 二、`collect_disk` 的单元测试

### 为什么

21 个判定 id 里，**它是唯一一个单元测试里一次都没出现过的**
（用下面这条随时可复核）：

```bash
grep -rhoE 'result_add[[:space:]]+"[a-z_]+"' rootfs/opt/klburn/ \
  | grep -oE '"[a-z_]+"' | tr -d '"' | sort -u
```

`e2e-qemu.sh --stage full` 会带到它，但那是 20 分钟一轮的端到端，
不适合当日常守卫。

### 怎么做

它在 `lib/collect.sh` 里，三条分支：

| 条件 | 期望 |
|---|---|
| `SMART_TARGETS` 为空 | WARN，文案「本机未安装硬盘」 |
| 有 `\|megaraid,` 项 | PASS，文案里带物理盘块数 |
| 普通盘 | PASS |

照 `tests/test-hw-checks.sh` 里已有的做法：直接给 `SMART_TARGETS` 赋值再调函数，
断言 `$LAST_STATUS`（那个文件里已经有好几处这么写）。

**顺手把文案过一遍禁词**：它是客户可见的，`FORBIDDEN` 扫描应该已经覆盖，
但值得显式加一条断言。

### 预估

1 小时。

## 三、shellcheck 收紧到 `-S info` 的分诊

### 为什么

现在 `tests/lint.sh` 跑的是 `-S warning`。收紧一档实测多出 **132 条**，
分布是：

| 码 | 条数 | 判断 |
|---|---|---|
| SC2317 | 84 | 测试里"先调用后定义"的打桩模式，**误报**，直接豁免 |
| SC2015 | 25 | `A && B \|\| C` —— **值得逐条看**，见下 |
| SC1091 | 9 | source 的文件找不到，误报 |
| 其余 | 14 | 逐条看 |

SC2015 这 25 条值得单独花时间：它正好对应
[§11-10](architecture.md#十一不变量清单改代码前必读) 那条真陷阱
（`... | grep -q X && echo yes || echo no` 在 pipefail 下，匹配成功反而走 `||`）。
大部分应该是测试里 `check(){ [[ ]] && ok || bad; }` 那种无害写法，
但**只要有一条落在判定路径上，就是一个潜伏的误判**。

### 怎么做

先只看 SC2015，逐条判断"这里 A 失败会怎样"。确认无害的，
在 `lint.sh` 的豁免清单里加一条并写明理由（那个文件有"豁免类数不超过 N"
的自检断言，加了要同步改上限）。真有问题的就改代码。

**别一次把 `-S info` 全打开。** 132 条里绝大多数是噪声，
一次性打开会逼着人加一大堆豁免，那条 lint 就废了。

### 预估

1~2 小时。

## 明确**不做**的，以及为什么

写在这儿是为了省掉下一轮重新推演一遍。

| 不做 | 理由 |
|---|---|
| **Ventoy 的 dm 设备链端到端** | QEMU 里没法真装 Ventoy。反查逻辑 `test-disk-exclusion.sh` 已用 loop + dm-linear 覆盖，e2e 这层加不了多少。真机上跑一次即可 |
| **报告的黄金文件快照**（存一份期望 HTML 去 diff） | 文案改一次就全红，很快会被人用 sed 批量"修好"，然后彻底失去意义。现在的**结构性**断言（章节数、判定条数、polyline 有没有）才是对的方向 |
| **把 `mutate.sh` 挂进 `run-all.sh`** | 它自己要调各个测试套件，挂进去就是递归 |
| **加 LICENSE** | 内部仓库，不开源不外发，已经确认过 |
| **折叠 `74e713c` / `b5df4f1` 那两个红 commit** | 已被 `v1.3.0` 的 tag 钉死，重写会让 tag 悬空。CHANGELOG 里记着这回事 |
