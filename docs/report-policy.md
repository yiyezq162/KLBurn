# 报告文案规范（内部）

> **这份文档是给我们自己看的，不随报告交付。**
> 它规定的是：哪些东西可以出现在交给客户的报告里，哪些绝对不行。

---

## 一、先分清各样产物的归属

| 产物 | 去哪儿 | 能不能给客户看 |
|---|---|---|
| **ISO 测试盘** | 硬件检测的软件环境；软件发布与硬件报告交付分开管理 | 不随硬件报告默认交付；独立软件发布须过授权、隐私及第三方许可闸门 |
| **工程目录**（`raw/`、`meta.json`、`results.jsonl`、`klburn.log`、各种 `.csv`、`SHA256SUMS`） | 内部留档，日后回档追溯用 | ❌ 不交付 |
| **内部工程报告**（`raw/INTERNAL_*.html` + 同名 `.pdf`） | 内部，我们自己复盘用 | ❌ **不交付** |
| **批次汇总 / 对比**（`tools/klburn-summary.py`、`klburn-diff.py` 的输出） | 内部，一批机器的产线视图 | ❌ 不交付 |
| **`报告名.html` + 同名 `.pdf`**（与报告目录同名的那两个） | **随机器交付给客户** | ✅ **只有它们** |

> 交付的那份**有六种形态**（全量 / CPU / 内存 / 显卡 / 硬盘 / 仅导出信息各一种），
> 在**随硬件交付的报告**中，归属没有例外：**只有和报告目录同名的那两个文件出门。**
> 六种形态各长什么样见 [`reports.md`](reports.md)，边界（也就是本文）对六种一视同仁。

这不禁止独立发布软件源码或 ISO。独立软件发布另遵守 [公开发布说明](publication.md)
和 [第三方分发边界](third-party.md)，必须先完成授权、当前文件与历史内容的隐私审查、
组件许可和必要源码提供义务核实。软件测试通过不代表这些闸门通过；本文不声明任何
候选 ISO 已具备公开分发条件。内部工程报告、客户资料与构建运维记录不因此转为公共附件。

所以：

- **工程目录和内部报告越详细越好** —— 命令原文、退出码、git hash、内部路径、
  盘里带了哪些工具、设备台账字段，全都可以往里塞。
  日后客户反馈问题时，这些是唯一的证据来源。
- **`报告名.html` 里假设读者是客户的采购或运维**，他不知道也不需要知道
  KLBurn 是什么、盘是怎么做的、我们的工具链长什么样。

## 二、客户报告里绝对不能出现的东西

### 1. 我们内部的实现细节

这条同时约束抬头和页脚：不额外披露内部工具链，版本可追溯性由
「报告版本」提供。PDF 的表格必须在 A4 可打印宽度内显示全部列，不能只验 HTML。
1.11.0 起中性报告品牌默认是 KLBurn；这是公开的报告抬头，不是工具链说明。
定制盘使用已提交的显示名称并标注“定制构建”，不因此放开源码路径、commit、
基础系统、工具列表或构建日志进入交付正文的限制。

| ❌ 不要写 | ✅ 改成 |
|---|---|
| 「本次测试介质未包含 NVIDIA 驱动」 | 「本次测试环境未包含显卡驱动」 |
| 「盘内缺少 gpu_burn 工具」 | 「本次测试环境未包含显卡满载测试程序」 |
| 「盘内没有 storcli64」 | 「当前测试环境的管理工具不支持该型号」 |
| 「把 storcli64 放进构建目录的 vendor/ 后重新出盘」 | 整句删掉 |
| 「盘内缺少 DHCP 客户端」 | 「当前测试环境不具备该项检测条件」 |
| 「未发现任何本机硬盘（只有U盘）」 | 「本机未安装硬盘」 |
| 「源码版本：5fb41af-dirty」 | 整行删掉（留在 `meta.json` 里） |
| 「测试工具 KLBurn vX（Ubuntu Server …，构建于 …）」 | 「报告版本 X」 |
| 「完整文件保存在报告目录的 raw/ 子目录下」 | 「以下为支撑本报告结论的原始采集输出」 |

判断标准很简单：**这句话里有没有只有我们才懂、或者只有我们才能去做的事？**
有就得改。客户看到「去 vendor/ 补个工具再重新出盘」，第一反应是"这机器是不是缺东西"。

抬头也受这条约束：客户只需要报告版本做追溯，不需要知道产品内部名、基础系统、
构建时间或源码 commit；这些完整保留在 `meta.json` 和内部工程报告。正文同样不出现
`raw/` 这类内部目录路径。

这条约束**不止管文案**，也管嵌进报告的原始日志：

- 采集失败的标记（`(command not found: storcli64)`、`(TIMEOUT after 20s: lshw)`）
  会被从嵌入内容里剔掉；整个文件只剩这类标记时，那一块整个不出现。
- 折叠块的标题里**不带 `raw/xxx.txt` 路径** —— 文件名往往就是工具名
  （`storcli-show.txt`、`gpu-smi-full.txt`），等于把内部实现直接印给客户看。

### 2. 让客户误以为机器有问题的措辞

**能力缺失 ≠ 硬件故障。** 我们的工具没带某个厂商的管理程序、驱动版本比客户的新卡旧，
是**我们环境**的限制，跟这台机器好不好毫无关系。这类情况：

- 状态一律判 **SKIP**，不判 WARN
  （WARN 会在报告抬头单独列一块，客户看到"告警"就会打电话问）
- 文案里必须明确写上一句 **「此项不影响整机结论」**
- 不要把原因归到硬件头上。写「当前测试环境未包含…」「驱动版本与该显卡不匹配」，
  不要写「阵列卡读不到固件版本」「显卡、供电或插槽异常」——后者听起来像客户的东西坏了

同理，**测试环境自身的问题绝不能判成硬件故障**。典型的是内存压测被 OOM killer
打死（退出码 137）：那是测试程序申请的容量超过了当时系统能给的，
和内存条好坏没有关系，必须判 WARN 并写明"不是内存故障"。

> 这条是有血的教训的。0.7.0 现场一台完全正常的机器，因为内存压测被 OOM 打死、
> 退出码 137 被当成"测试进程异常退出"判了 FAIL，硬生生被拦在出货前。
> **把好机器拦在出货前，比漏判更糟。**

### 3. 与判定无关的数据

报告里只放**参与判定、或者支撑判定**的数据。硬盘的寿命类字段
（通电时间、通电次数、累计读写量、已用寿命、异常掉电次数）不在此列：
它们既不参与判定，也回答不了"这台机器合不合格"。

盘的结论看的是 SMART 健康状态和坏道计数在压测前后有没有增长，这两样报告里都有，
逐盘列出。寿命类字段完整保留在工程数据和内部报告里，做设备台账和日后回查用。

写文案时同理：介绍内存条明细就写「可逐条核对品牌与规格是否一致」，
说清楚这张表能拿来做什么，不必替客户引申。

**这条尺子对所有数据成立，不只是硬盘。**判断只问一句：

> **这个数字，客户拿它能做出"收还是不收"的决定吗？**
> 不能，但看了会想问 —— 那就是内部的。

凡是讲"**这台机器过去经历了什么**"、而不是"**这一轮测出了什么**"的读数，
一律归内部。1.9.0 新增的显存那几格是同一类（`INTERNAL_ONLY_METRICS`）：

| 读数 | 为什么不进交付报告 |
|---|---|
| 显存重映射不可纠正行 | 出厂以来累计被永久屏蔽过几行，和通电时间同一类；客户看到一个孤零零的 `5` 只会问"那是什么，严重吗" |
| 显存 ECC 可纠正 / 不可纠正 | 是那条结论的原始读数，而结论那句话已经把数字连同含义一起说清楚了；表里再印一个裸数字就是同一个数印两遍（见第 10 条） |
| 显存 ECC **分项**（SRAM / DRAM 各可纠正、不可纠正，1.10.2） | 同上：结论里已经写成"其中显存颗粒（DRAM）不可纠正 2 次"，含义和数字一起给了 |
| 显卡热降频采样占比（1.10.2） | 结论里已经写成"N 次采样中有 M 次显卡自报正因过热降频"；表里一格裸的 `3/1240` 只会让人问这是什么 |

> **一条明写的例外：显卡芯片内缓存（SRAM）的历史累计错误**「进」**交付报告**
> （1.10.3，用户 2026-08-20 拍板）。
>
> 按上面那把尺子它本该归内部 —— 累计 = 出厂以来。**但 SRAM 这一路不一样：
> DRAM 坏了有行重映射兜底**（坏块整行换掉，`check_gpu_remap` 已经在看），
> **而芯片内缓存没有任何替换机制** —— 它坏过就是坏过，没有备用的可换。
> 所以它回答的不是"这台机器过去经历了什么"，而是"**这张卡本身现在有没有
> 毛病**"，和硬盘通电时间不是一类东西。
>
> 它自成一条判定（`check_gpu_ecc_aggregate`「显卡缓存历史错误」），
> 和「显卡显存 ECC」那条**本次上电以来**的分开写 —— 两个问题混进一句话，
> 看报告的人分不清刚测出来的和这张卡以前就有的。
>
> ⚠️ 判 FAIL 的依据**只能是显卡自己给的那个标志**（`SRAM Threshold
> Exceeded: Yes` = 厂家说这张卡该返修了），不许我们定"多少次算坏"
> （四号红线）。累计不可纠正 > 0 判 WARN，形状和行重映射那条一模一样。

> ⚠️ 藏的只是**「其他实测指标」那张表里的裸数字**。`check_gpu_ecc` /
> `check_gpu_remap` 两条判定连同 WARN / FAIL 全文照常进交付报告 ——
> **任何 WARN / FAIL 一条都不许藏**那条红线一步都不能退。
> `test-internal-report.sh` 里这一组是**三头**钉的：交付报告没有裸数字 /
> 交付报告有 WARN 结论 / 内部报告一个字段都不少。少钉一头，另外两头
> 都能装成绿的（比如一条"gpu 组整组丢掉"的错误改法）。
> 变异 `gpumem-history-leak` 守着。

### 4. 现场主动跳过的那一项（1.7.6 起）

**硬盘压测没跑时，和它相关的项整个不进客户报告。** 具体是：逐项结论里的
「硬盘压力测试」和「硬盘 SMART 复查」、1.4 表格的「本次压测」列、
压测时长表的「硬盘压测时长」、以及指向 SMART 复查那一节的那句话。

理由：现场 99% 会跳过硬盘压测（客户不让往盘里写破坏性数据）。留着一行
「SKIP 硬盘压力测试 现场选择跳过（直接回车）」，客户看到的是「他们少测了一项」——
而那恰恰是客户自己的选择。这是白惹一次解释，不是透明。

**这是「藏」，不是「删」。** `results.jsonl` 一个字段都没少，内部工程报告
照常全列。客户报告是**交付物**，它要回答的是"这台机器合不合格"，
不是"我们的流程跑了哪几步"。

> ⚠️ **只藏 PASS / SKIP。WARN 和 FAIL 一条都不许藏。**
> 「硬盘 SMART 复查」判 FAIL 的意思是这一轮盘上新增了坏道 —— 那和跑没跑
> 硬盘压测无关（CPU/内存压测照样跑了十几分钟），是实打实的硬件问题。
> 藏掉它等于让一块正在坏的盘拿着一份干净报告出厂。
> 少写一行 SKIP 最多惹客户问一句，这个是把坏货放出去，两件事不是一个量级。
> `test-report-render.sh` 有成对断言，`mutate.sh` 里 `disk-hide-fail` 守着。

**这条规则不要随手推广到别的项。** 它成立的前提是「跳过是客户自己当场选的、
而且这一项 99% 都不跑」。别的 SKIP（平台不提供某个计数器、这台机器上压根
没有可测的东西）仍然要如实列出来并写「此项不影响整机结论」——
那些讲的是**被测机器**的事实，客户有权知道哪些没查过。

> ⚠️ **1.9.4 从这条里切走了一类：「我们没带那个程序 / 没量到」。**
> 那类 SKIP 讲的不是被测机器，是我们自己，见下面的 4-2。

### 4-3. 单项专测：照采不照报（1.9.8 起）

1.9.7 那份**硬盘专项**报告里有：逐路 CPU 频率与缓存、逐条内存明细、整张网卡表、
GPU、电源、PCIe 链路、平台关键设置、固件版本清单、四十万字符的 dmidecode 原文，
外加一条「内存混插 WARN」。客户拿到的是一份自称"本轮只对硬盘做了压力测试"、
却铺了满屏其它部件的报告。

**单项专测是一把独立的工具，不是"全量报告删几行"。** 拿去测硬盘的人要的是
一份硬盘测试单，上面写清楚这是哪台机器（整机 / CPU / 内存）就够了。

`raw/`、`results.jsonl`、内部工程报告**一个字都不少**（日后排查全靠它们），
只有交付报告按范围裁：

| 范围 | 硬件清单 | 配置核对 | 原始日志 |
|---|---|---|---|
| `full` / `info` | 8 节全出 | 四小节全出 | 全部 |
| `cpu` / `mem` | 整机 / CPU / 内存 | 只留被测部件那几条结论 | 只留对应部件 + 本轮真跑过的 |
| `gpu` | + GPU | 同上 | 同上 |
| `disk` | + 硬盘、阵列卡（盘挂在卡后面） | 同上 | 同上 |

- 平台身份那三节里，**不是被测部件的那个给简版**：CPU 只留型号 / 路数那张表，
  内存只留装机容量 / 条数。
- 「平台关键设置」「核对依据的实测值」「固件版本清单」三张表只进 `full` / `info`。

> ⚠️⚠️ **只藏 PASS / SKIP。WARN 和 FAIL 一条都不许藏。**
> 和上面第 4 条那把尺子完全一样。只压了 CPU 的那一轮里 PCIe 报了新增 AER、
> BMC 记了电源掉电，那仍然是**这台机器**的毛病，和压了哪个部件无关；
> 藏掉 FAIL 更是让报告打着红色大字、底下找不到任何理由。
> **范围裁掉的是"没话说的行"和整块的清单表格，不是"这台机器有什么毛病"。**
> `mutate.sh` 里 `scope-filter-hides-bad` 守着。

### 4-2. 「我们没测到」的那些 SKIP（1.9.4 起）

1.9.3 的交付报告里印过这两行：

```
SKIP  CPU 计算正确性    当前测试环境未包含处理器计算正确性诊断程序，本项未做核对。
SKIP  显卡专项诊断      当前测试环境未包含显卡厂商诊断程序，本项未做核对。
```

客户读到的不是「这台机器没问题」，是「**这家供应商的工具箱是破的**」。
上面第 4 条那句「客户有权知道哪些没查过」在这里不成立：**我们没带程序，
跟他那台机器好不好毫无关系**，这一行对他做「收还是不收」的决定
没有任何帮助 —— 它属于第 5 条那一类（判的是我们、不是机器）。

**不是把那两行删掉了事**，那样下次又会长出第三行（这件事已经被客户说过两次）。
判据放在**产生这条结论的地方**：

```bash
result_add "<id>" "<名字>" "$ST_SKIP" "<文案>" "<证据>" "self"
#                                                        ^^^^ 第六个参数
```

`origin=self` 的意思是「这条 SKIP 的原因在我们这边，不在被测机器上」。
`generate_report.py` 只认这个字段，**不去猜文案** —— 猜文案的做法
（「看看句子里有没有'未包含'」）改一次措辞就会静悄悄失效，
而失效的方向是漏出去。

三条边界，一条都不能松：

| | |
|---|---|
| **只藏 SKIP** | 部件自己给的 FAIL（诊断判出「这颗 CPU 会算错」）是真故障，一条都不许藏 —— 见下面 5-2 最后那段 |
| **判据是 `origin`，不是文案** | 别改成关键字匹配 |
| **「这台机器上没有可测的东西」不是 self** | 「本机只安装了 1 张显卡，没有卡间互联可测」「未发现可测试的本机硬盘」讲的是被测机器的事实，照常印。那几处不传 `origin` |

`results.jsonl`、内部工程报告、屏幕输出全都一个字不少。
`test-report-render.sh` 里这一组是**四头**钉的（两行不外发 / 机器事实照常印 /
带 origin 的 FAIL 照常印）。

**同一把尺子还切走了「序列号一致性」**（`check_sn_consistency`，1.9.4）：
它查的是**文书**对不对得上（主板 BIOS / BMC / 机身标签三处），不是硬件有没有毛病，
而整机结论只回答后者。组装机上 BIOS 那一格本来就没人填、也没地方填，
报告于是每台都挂一条黄的「建议出货前在 BIOS 中补写」——
客户读到的是「这台机器有问题」，而它连硬件都不是。
整条走 `INTERNAL_ONLY_ROWS`。
⚠️ **藏的只是那条判定，整机序列号本身照常印**（抬头 + 1.1 整机那张表）——
连序列号一起藏掉的话这份报告就对不上机器了，那是另一种翻车。

### 5. 判的是我们、不是机器的那些项（1.7.7 起）

判断标准只有一句：

> **这一项要是失败了，客户会在意吗？**

- `collect_deep`（扩展信息留档）失败 = 我们自己的存档薄了一点，客户拿到的报告
  一个字都不少 → **不进客户报告**（无条件，任何状态都不进）
- `collect_system`（硬件信息采集）失败 = 报告里整块硬件清单都没了 →
  客户当然在意，**留着**

它的原文案「已完整保存……供日后追溯」本身也是内部口径，按上面第 1 条就不该外发。

**同一把尺子也用在「模棱两可的提示」上。** 典型是阵列卡那条：PCI 上没有卡、
BMC 为阵列卡预留的传感器又全无读数时，可能是「本来就没装」，也可能是
「卡坏到 PCI 都枚举不到」——**分不开的东西不该去染客户的结论**。
这类提示的出口是：现场屏幕 + `klburn.log`（操作员当场能去摸一把卡）、
`raw/` 留档（内部报告查得到），客户报告里只写确定的那部分（「未安装阵列卡」）。

> 反例长这样，别再写回去：
> 「未安装阵列卡；BMC 上为阵列卡/HBA 预留的传感器均无读数……如果确实装了卡，
> 建议检查卡和转接板/riser 是否插到位」——
> 一台压根没打算装卡的机器，客户读完会以为自己的卡松了。

**这把尺子也管「其他实测指标」那张表**（1.8.3 起）。`cpu / 失败压测项` 是
stress-ng 内部子测试的失败计数：客户看到一个 `0`，既不知道分母是多少，
也不知道它和上面那条 PASS 有什么区别 —— 有区别时上面那条就不会是 PASS。
过滤在 `generate_report.py` 的 `INTERNAL_ONLY_METRICS` 里，和判定行的
`INTERNAL_ONLY_ROWS` 是同一个机制。**这是"藏"不是"删"**：`metrics.jsonl`
和内部报告一个字段都没少。

### 5-3. 纯采集行的 PASS：没话可说就别占一行（1.10.1 起）

第 5 条那句尺子（「这一项失败了，客户会在意吗」）一直是对的，
只是以前把它实现成了**整个 id 无条件留着**。于是每份报告里都有这七行：

```
PASS  硬件信息采集   主板/BIOS/CPU/内存信息采集完成
PASS  硬盘信息采集   共 1 块盘，已采集型号/序列号/固件/容量与 SMART 健康状态
PASS  网卡          共 4 个物理网口，已采集型号/固件/协商速率/链路状态
PASS  GPU          识别到 1 张显卡：0, NVIDIA RTX A6000
PASS  IPMI/BMC     BMC 在线，已采集传感器读数；测前 SEL 共 114 条
PASS  阵列卡        已采集阵列卡型号、固件版本与逻辑盘状态。阵列卡不做压力测试。
PASS  扩展信息留档   已完整保存本机的固件版本、插槽、传感器…
```

它们说的全是**"我们跑过这条命令了"**，一个字都不回答「这台机器硬件有没有毛病」。
而采到的东西本来就在「一、硬件清单」里逐条摆着：板号、BIOS 版本、
每块盘的型号序列号、每个网口的型号固件、每张卡的型号 ——
客户要核对的是那几张表，不是这里的七行"完成"。
一份 47 条判定的报告里有 8 条是这种，读的人得先把它们跳过去才找得到真正的结论。

> 这和 1.9.9 砍掉那条「电源少一路交流输入」的误报是同一件事：
> **一条永远没有信息量的行，唯一的作用是训练看报告的人跳行** ——
> 而那反过来会让真正该看见的那条被一起跳掉。

⚠️⚠️ **只藏 PASS。WARN / FAIL / SKIP 一条都不许藏。**
同一个 id 在别的状态下句句是实话，而且往往是最要紧的那句：

```
WARN  硬盘信息采集   本机未安装硬盘（未检测到任何内置存储设备）
WARN  网卡          未发现物理网口
FAIL  硬件信息采集   未能读取主板 BIOS 记录的硬件信息
FAIL  阵列卡        阵列卡报告逻辑盘降级
SKIP  GPU          未安装独立显卡
```

这些讲的是**被测机器的事实**，客户有权知道 —— 和 4-2 那条 `origin=self` 的
边界是同一把尺子（「这台机器上没有可测的东西」不是 self）。

⚠️ `check_psu`（电源）**故意不在这张名单里**：它的 PASS 文案说的是
「交流输入与模块状态均正常」/「PSU3 本次未接入交流电…仍具备电源冗余」，
那是实打实的判定结论，不是"我们采集完了"。

名单在 `generate_report.py` 的 `COLLECT_ONLY_ROWS` 里，和 `INTERNAL_ONLY_ROWS`
挨在一起 —— 区别是前者**看状态**、后者无条件。`test-report-render.sh` 里是
**成对断言**：藏了 PASS + 同一条改成 FAIL/WARN 之后必须还在。

### 5-2. 客户会拿它去找机器毛病的那些项（1.9.2 起）

第 5 条问的是「这一项失败了，客户会在意吗」。1.9.2 加了一个反过来的问题：

> **这一项就算没失败，客户看了会不会开始怀疑这台机器？**

典型是 `fwts`（固件 / ACPI 合规检查）。这一层以前完全没查过，加得对 ——
但**完全正常的服务器上 ACPI 告警极其常见**，几乎每台都有若干条。印进客户报告
就是每台机器都刷一片黄，而且刷的是客户看不懂、也无从处理的东西。
和 0.6.0 把 CPU 告警线定在 88°C 时每台机器都刷黄，是同一个毛病。

它对**我们**有价值（同一批板子的 BIOS 有没有共性问题），所以走
`INTERNAL_ONLY_ROWS`：`results.jsonl` 和内部报告一个字段都没少，只是不外发。

> ⚠️ 这是「只藏 PASS/SKIP，WARN 和 FAIL 一条都不许藏」（二-4）**唯一的例外**，
> 必须说清楚为什么不矛盾：那条红线管的是**"这台机器有没有毛病"的判定**，
> 而 `collect_fwts` 和 `collect_deep` 一样属于"判的是我们、不是机器"
> （第 5 条那一类），整机结论也不看它。
> `test-internal-report.sh` 里有三头成对断言，变异 `fwts-to-customer` 守着。

**同一把尺子也用在校验清单上。**`SHA256SUMS`（报告 + `raw/` 全量的 SHA256）
只落文件、只写进内部报告：客户手上没有 `raw/`，拿到一个哈希也校验不了任何东西，
印在交付报告上只会招来"你们是不是怕被改"的提问。它的用途是**我们自己**的 ——
半年后客户拿一份报告回来问，我们能证明归档的和他手上的是不是同一份。

**反过来，这条不能被滥用成"坏消息也别说"。**1.9.2 同时加了四条
"设备自己给结论"的判定（网卡 / 硬盘自检、处理器计算正确性、显卡厂商诊断），
它们**全部进客户报告，而且判 FAIL** —— 部件自己说它没通过，那就是真故障。
裁的是"会引起无谓怀疑的无关信息"，不是"坏消息"。

### 6. 读不出来的标记、和不是实测值的数字（1.8.3 起）

采集工具对"这一格读不到"有它自己的写法，**那些写法不是内容**，照抄进客户报告
就是一格乱码或者一个荒唐的数字：

| 原样 | 真正的意思 | 报告里应该是 |
|---|---|---|
| `<BAD INDEX>` | dmidecode：BIOS 把字符串下标填到了字符串表外面 | `—` |
| `<OUT OF SPEC>` | dmidecode：枚举值不在 SMBIOS 规范里 | `—` |
| `65535 W` | SMBIOS 的 16 位整数填了 `0xFFFF`，即"没填" | `—` |
| `Serial Number: N/A` | BIOS 没填整机序列号 | 退到主板序列号 |
| 显卡 `Serial Number: 0` | 消费级卡本来就没烧序列号 | `—` |

> **占位符名单在 shell（`junk()` / `_serial_is_bogus()`）和
> Python（`BOGUS`）里各有一份，必须一致。**海光那台的 `N/A` 就是只有 Python
> 认，于是报告抬头「整机序列号 NA」，而主板序列号是真的、就在同一份 DMI 里。

两条配套的：

- **"读不出身份" ≠ "这个部件不存在"。**Supermicro X11DPG-QT 那两路电源身份
  全是 `<BAD INDEX>`，它们是真电源（BMC 报 `Presence detected`）。
  判空槽位的判据仍然只有"额定功率**显式为 0** 且身份全是占位符"。
- **一整行都是破折号时要就地解释一句。**「本机 BIOS 未填写……读不到不代表电源
  有问题」——不解释的话每台机器都要口头解释一遍，而且很容易被当成漏采。

同一类还有**照抄工具原文**：`Present, OK` / `Populated, Enabled`（DMI 的英文
状态）、`55 MiB (2 instances)`（lscpu 的英文尾巴）、
`rtl_nic/rtl8168d-2.fw`（ethtool 给的固件文件名，带目录，看着像路径）。
翻译或裁剪，但**数字和信息量一个都不许少**——多段版本号
（`1.63, 0x800009fb, 1.791.0`）就原样留着，别拿一个 `/` 去切人家的版本串。

### 6-2. 采集和压测工具的名字（1.8.4 起）

第 1 条说的是「盘里**缺**哪个工具」。反过来那一半一样不能写：
**盘里带的是哪个工具，客户同样不需要知道。**

| ❌ 不要写 | ✅ 改成 |
|---|---|
| `stressapptest 测试 246632MB（占系统识别内存 …）` | `覆盖 246632MB（占系统识别内存 …）` |
| `stress-ng 报告 3 个压测项失败` | `CPU 压测报告 3 个子项失败` |
| `gpu_burn 报告 2 张卡 FAULTY` | `满载测试报告 2 张卡状态异常` |
| `dmidecode 读取失败，无法获取主板信息` | `未能读取主板 BIOS 记录的硬件信息` |
| `（或 ethtool 读不到速率）` | `（或网卡未上报协商速率）` |
| `数据来自 nvidia-smi` | `数据取自显卡驱动的实时读数` |
| 折叠块标题 `dmidecode 全量输出` | `主板与整机信息（BIOS 记录）` |
| 「其他实测指标」里的 `mem / 测试工具 / stressapptest` | 整行不进客户报告 |

**数字和结论一个都不许改**，改的只是那个专有名词。

这一条 1.8.4 之前一直漏着，原因值得记下来：禁词表里只有 `storcli`，
因为**只有它咬过人**。别的工具名判据完全一样，只是没人把词加进去。
现在 `FORBIDDEN` 里工具名是成组的。

> **工具名会从两条路进报告，两条都得堵：**
>
> 1. **源码里的中文文案**（`result_add` 的 detail、报告生成器里的中文串）——
>    `tests/test-hw-checks.sh` 的 `FORBIDDEN` 扫得到。
> 2. **数据的值**（`metrics.jsonl` 里 `mem / 测试工具` 的值就是工具名）——
>    源码里 grep 不到，只能查**生成出来的 HTML**。
>    `tests/test-report-render.sh` 那一组就是干这个的。
>
> 1.8.4 之前只有第 1 条，而漏出去的那个正好走的是第 2 条。
> 变异 `metric-tool-name` 和 `result-tool-name` 分别钉这两条路。

**`<pre>` 里嵌的原始日志不受这条约束** —— 那是存证，不是结论
（第 1 条只要求剔掉采集失败标记、折叠块标题不带 `raw/` 路径）。

### 7. 屏幕输出的英文

屏幕（Linux 文本控制台）显示不了中文，所以运行时输出一律英文；
但那些英文是给现场工程师看的，**不进报告**。
`result_add` 的 `detail` 字段是中文、只进报告，屏幕上只打 id 和状态。
这两套文案不要混用。

### 8. 配置类与性能类结论的措辞（1.9.0 起）

各家的出厂验收表里，除了"坏没坏"之外还有两类要求：**一致性**（内存 PN 一致、
同规格网卡固件一致）和**性能数值**（带宽多少、算力多少）。
这两类各有一条措辞红线，都很容易写错方向。

**（1）一致性不符是"配置问题"，不是"这台机器坏了"。**

混插的内存、两批不同固件的网卡，机器照样正常工作。这类一律判 **WARN**，
措辞的主语必须落在**配置**上，不能落在**故障**上：

| ❌ 不要写 | ✅ 改成 |
|---|---|
| 「内存条异常：检测到 2 种颗粒型号」 | 「本机装有 8 条内存，规格不完全一致：颗粒型号 2 种（…）。混插不影响机器正常工作，但整机内存会按最低规格的那一条运行，建议出货前按订单要求确认。」 |
| 「网卡固件版本错误」 | 「同型号网卡的固件版本不一致：…。建议出货前统一固件版本。」 |
| 「序列号错误」 | 「整机序列号在两处记录不一致：主板 BIOS 为 A，管理控制器为 B。建议出货前统一，并核对机身物理标签。」 |

**（2）性能数字只报不判 —— 报告里不许出现"参考值 / 是否达标"这类东西。**

⚠️ 这一条 1.9.0 中途改过一次，理由要写清楚，别再改回去。

一度做过一整套阈值：把某一份订单上的数字写进 `klburn.conf`，跑完拿去比，
不达标就判 FAIL。**整个删掉了。** 因为这张盘是**插上就跑、无人值守**的：
现场没有人、也没有地方去填"这台机器的带宽应该是多少"。凭空写一个数进来，
等于我们替客户定了一个他没定过的标准，再拿它去说这台机器行不行 ——
那个数字从哪来的谁也说不清。

而且**别人的验收标准不是我们判定机器合格与否的标准**。
整机结论回答的始终只有一件事：**这台机器的硬件有没有毛病。**

所以性能类结论的写法只有一种：**如实报出实测值，句号。**

| ❌ 不要写 | ✅ 改成 |
|---|---|
| 「内存读取带宽 245678.9 MB/s，低于验收标准（430080 MB/s），未达标」 | 「内存满负载读取带宽实测 245678.9 MB/s（本机内存运行频率 4800 MT/s，已装满 16 个通道）。」 |
| 「CPU 算力 3010 GFlops，未达到 3600 的要求」 | 「全核浮点矩阵运算（问题规模 40000 阶，重复 4 次取最好成绩）的平均算力实测 3010.0 GFlops。」 |
| 「本次未设定该项的验收标准」 | 整句删掉 —— 提"标准"两个字本身就是多余的 |

对应到状态上：基准项只有 **PASS（量到了）** 和 **SKIP（量不到）**，
**不会是 WARN，也不会是 FAIL**，更不影响整机结论。
报告在那一节的开头会明写这一点，让读的人知道该拿自己的要求来对。

**（3）把"是怎么测的"写进那句话里。**

一个孤零零的数字没法用。带宽要说清是哪个方向、多大块、队列多深；
算力要说清矩阵多大、跑了几次；内存带宽要说清频率和插了几个通道 ——
拿这个数去对任何标准的人，都需要这些前提。
**但只写一遍**：这些前提写在结论那句话里就够了，底下不要再拿一张表
或一行"测试条件"重复一遍（见第 10 条）。

### 9. 分节只决定"印在哪一节"，绝不决定"印不印"（1.9.0 起）

1.9.0 把客户报告的判定拆成三段（配置核对 / 性能基准 / 压测与复查），
分法是按"读者关心的三件事"来的：装的东西对不对 / 跑多快 / 扛不扛得住
（各家的出厂验收表基本也是这么分段的）。这个改动**唯一不能犯的错**是：

> 分组表里没登记的 id，必须落到"压测与复查"那一段，
> **而不是从报告里消失**。

一条判定凭空消失比它出现在一个不太贴切的小节里严重得多 —— 前者是
"既不是 PASS 也不是 SKIP，看报告的人根本不知道这一项测没测"，
和 §2-4「藏」那件事的性质完全不同（那个是有意的、只藏 PASS/SKIP、
数据一个字段没少）。

`generate_report.py` 里 `other_rows` 用的是**排除法**（不在 CONFORM_IDS、
也不以 `bench_` 开头的都归它），就是为了让"忘了登记"的后果止步于分错节。
`test-report-render.sh` 有一条「判定总条数一条都不许少」钉着，
`mutate.sh` 的 `accept-group-drop` 守着。

**「性能基准」整节是有条件的**：这一节**画不出任何东西**时整节不出现，
后面的一级编号跟着往前顺延。理由和 §2-4 一样 —— 一台不做性能验收的机器，
报告里多出一节全是 SKIP 的"基准"只会招来"你们是不是没测"的提问。
**但这只对整节成立**：只要跑了一项，那一节里所有状态照常全列。

> **判据只能是"这一节真的画得出东西"**（有 `bench_*` 判定行、或有逐盘带宽表），
> 不能顺手把 `metrics_of("bench")` 也算进去。bench 组的指标在这一节里
> **一格都不单独印** —— 每个数字都已经写在对应那条结论的句子里（见第 10 条）。
> 拿它当判据，遇到"有 bench 指标、却一条 bench 判定都没有"的 run-dir 就会画出
> 一个只有标题和导语、底下什么都没有的空章节。
>
> 反过来那一半同样要守：**整节没画时，那几个指标必须退回「其他实测指标」**，
> 不能因为"它们本该有自己的小节"就两头不落、从报告里凭空消失 ——
> 那就退化成第 9 条开头说的那件事了。变异 `bench-empty-section` 守着。

### 10. 同一个数字只在一处出现（1.9.0 起）

报告是要发给客户的，**排版本身就是内容的一部分**。这一版踩过两次同一个坑：
在结论列表之外又加一张"实测数值汇总"表、在结论下面又加一行"测试条件"——
两样都是把上面刚说过的数字再印一遍。

> 同一页上同一个数出现两次，那不是排版，是堆砌。

判断标准很简单：**加一块东西之前，先问它有没有带来新信息。**

- 逐盘的带宽表 —— **留**：结论那一行给不出逐盘明细，这是另一组数
- 六个整机数字的汇总表 —— **删**：每条结论里已经写着那个数
- "测试条件：矩阵 40000 阶" —— **删**：那句话就在 CPU 算力那条结论里
- 平台设置的值 —— 只在「平台关键设置」那张表里出现一次，
  判定行改成「已读取本机 N 项…（见下方）」

配套的一条：**二级编号必须是动态生成的**。小节是"有数据才画"的，
编号写死就会断号（没显卡时 5.6 直接跳 5.8），读的人第一反应是
"报告漏了一节"。两份报告都已经改成动态编号，
`tests/test-internal-report.sh` 里有断号守卫。

### 11. 指路不许指空，标题不许说得比测得多（1.9.1 起）

小节标题是"有数据才画"的，**而且标题本身也会跟着数据变**。逐盘带宽那张表
就是：现场没确认破坏性写入时只测得到读，写那一列整个不画，标题也只能写
「硬盘顺序读带宽」——写死成「顺序读写」就是第六节第 4 个自查问题
（说得比测得多），一张只有读带宽的表顶着"读写"的标题，客户会问"写的数呢"。

配套的两条：

- **判定文案里那句「……见下方「X」」必须指得中。** X 是某个小节的标题，
  而标题会变、小节还会整个消失。1.7.6 那句指向被藏掉的 SMART 复查是同一个毛病，
  当时是靠人眼看出来的。现在 `test-report-render.sh` 里有一条
  「每个「见下方「X」」都得有对应标题」的守卫，两处字面量的对账在
  `test-hw-checks.sh`（判定文案在 shell、小节标题在 Python，改一边忘一边就红）。
  **所以这两个标题在两边都要写成字面量，不许拼**。
- **表里那一列"测试口径"要对得上它标的那一格。**逐盘表里读和写各有一个
  job 名（`libaio_read_128k_32_1` / `libaio_write_128k_32_1`），
  写成"后写的覆盖先写的"就会让「顺序读带宽」那一格顶着一个 `_write_` 的口径。
  数字没错，但标错了它是怎么来的 —— 而这张表存在的全部理由，
  就是客户拿它去和自己验收单上的 job 名对照。
  变异 `bench-caliber-overwrite` / `bench-title-static` / `bench-pointer-static` 守着。
- **拆开或拼起来的数字都要带单位**（1.9.2 补，同一件事栽第二次）。
  1.9.1 是**拆没的**：逐卡满载读数拆进表格之后单位丢了
  （「距温度上限最小余量 8」—— 8 度还是 8%？）。
  1.9.2 是**拼漏的**：传感器判定里那个上下限只写了数字
  （「96 °C，高于主板设定的告警上限 95」—— 95 什么？）。
  结构化数据里不塞单位是对的，**但拼成给人看的那句话时必须补回去**。
  两次都是把报告当成品逐格读才看出来的，断言全绿。

### 12. 同一个数字，报告里只能有一个口径（1.9.2 起）

r08 那份真机报告上印过：

> 平均频率 2686MHz　　最低频率 2688MHz

最低的比平均的还高。两个数都没算错 —— 最低值跳过了压测开头两个空载采样点，
平均值没跳，是**两个窗口**。但客户不会去想"哦这是两个口径"，他想的是
**"这报告算错了"**，而一份被怀疑算错了的报告，后面每一个数字都要重新解释一遍。

规矩：**成对出现的数（最低/平均、前/后、总数/其中几项）必须出自同一组样本。**
实现上不要靠断言去兜，要靠**只留一个取样口**——
`phase_freq_stats` 和 `gpu_load_stats` 各自一次算出全部值，
这样 `min ≤ avg` 是结构上成立的，将来也没人能把它们改回两个窗口。
变异 `freq-window-split` 守着。

### 13. 单项专测的报告不许看起来像"全测过了"（1.9.5 起）

1.9.5 起可以只测一个部件（CPU / 内存 / 显卡 / 硬盘），也可以只导出一份硬件
信息。这带来了一个**这份规范里最危险的新失效方式**：

> 一台只测了 CPU 的机器，报告上打一个和全量测试**一模一样**的绿色 PASS。
> 半年后拿着这份报告，没有任何人分得清它到底测过什么。
> **这比不做这个功能还糟** —— 它把"没测"包装成了"通过"。

所以范围模式下多四条硬性要求：

1. **抬头第一行写明本轮范围。**排在整机序列号**前面** —— 读这份报告的人要回答
   的第一个问题是"这台机器测了什么"，不是"它测了多久"。
2. **结论块下面紧跟一句"哪些部件这一轮没测"。**必须紧贴结论，不能埋到下面
   某一节里：一个孤零零的 PASS 加上一行"本轮只测了 CPU"，和一个孤零零的
   PASS，是两份完全不同的报告。
3. **「仅导出硬件信息」那一档不出 PASS 大字。**那一轮一个压测都没跑、
   一个部件都没验过，报告里没有任何东西支持"合格"这个结论。
   换成灰色的「仅硬件信息 · 未做测试」，并写明**不能作为出厂验收依据**。
   —— FAIL 照打不误：那一档里 FAIL 的来源是采集或配置核对真的判出了问题
   （内存容量对不上、看到虚拟设备），那是实打实的、必须看见的东西。
4. **报告文件名和目录名带范围后缀**（`_Full` / `_CPU` / `_MEM` / `_GPU` /
   `_DISK` / `_INFO`）。后缀只能是 ASCII —— 那个串同时要当 exFAT 目录名，
   也会打在 Linux 文本控制台上。中文范围名只出现在 HTML 里。

#### 裁法

- **「一、硬件清单」八个小节在所有范围下都完整保留。**那正是做单项测试的人
  也要核对的"平台参数"，而且"没装的硬件标未安装、不是整节消失"（§三）
  这条不因为范围而松动。
- **「二、配置核对」保留。**它回答"装的东西对不对、齐不齐"，便宜且有用。
- **「三、性能基准」「四、压力测试结果」按范围裁**：不在范围里的判定行压根
  不存在（**整项不跑，不是跑了再藏**），对应的图表小节也不画，
  整节都空了就整节不出现。裁完**编号不许断号**，判定文案里的
  「见下方「X」」不许指向一个不存在的小节（§11 已经管着这两条，这里只是
  重申它在范围模式下同样成立）。
- **范围外的压测时长不许印一行"0 秒"。**读的人会以为那一项失败了，
  而这一轮压根没打算测它。（硬盘那一行 1.7.6 起就是这么做的，这里是推广。）
- **范围内的那个部件反过来写得更细**：CPU 专测多一节「逐颗 CPU 满载温度」、
  内存专测多一节「逐条内存 ECC 计数（压测前后对比）」、显卡专测多两条逐卡
  频率/风扇曲线、硬盘专测多一节「逐盘 SMART 关键项（压测前后对比）」。

  ⚠️ **加细不等于放宽红线。**这些小节里的每一格都必须是参与判定、或直接说明
  本轮测量的数据。寿命类字段（通电时间、累计写入量、磨损百分比）在**任何**
  范围下都不进交付报告（本节第 3 条），哪怕这一轮就是硬盘专项测试。

`tests/test-report-render.sh` 里每个范围各生成一份报告逐条断言，
`tests/mutate.sh` 的 `info-scope-green-pass` 守着第 3 条。

## 三、客户报告里应该有的东西

- 这台机器装了什么（型号、序列号、容量、固件版本），**有啥列啥，没有的标"未安装"**
- 每一项测了什么、结论是什么、依据的实测数据是什么
- 温度/功耗曲线，让客户看得见机器真的被压过
- 判定阈值（显示的是本次**实际生效**的值，取自 `meta.json` 的 `thresholds`）
- 整机结论：**只看有没有 FAIL**，SKIP 和 WARN 都不拉低结论
- 但**一条判定都没有时不许显示 PASS**：那说明这轮压根没跑成。这种情况结论判 FAIL，
  并写明「本次测试未产生任何判定结果，本报告无效」。
  措辞只说**这次测试**没跑成、请重测，**绝不能借用真 FAIL 那句「不建议出货」** ——
  机器没被评估过，我们没有任何依据说它不好。`test-report-render.sh` 里有断言守着。

## 四、内部工程报告可以写什么

反过来，`raw/INTERNAL_*.html` 是写给我们自己的，**该说的都要说清楚**：

| 类别 | 例子 |
|---|---|
| 不参与判定的字段 | 通电时间、通电次数、SSD 已用寿命、异常掉电次数 |
| 我们这一轮环境的缺口 | 盘里没带 storcli64、某条采集命令超时了、没能联网校时 |
| 版本可追溯 | KLBurn 版本、源码 commit（含 dirty 标记）、构建日期、驱动版本 |
| 二次解读 | 逐颗 CPU 温差、内存混插、插槽利用率、PCIe 链路降级、光模块收发光功率 |
| 主观评价 | 「这台机器哪里好、哪里将来可能出问题」，分 良好 / 关注 / 风险 / 记录 四级 |

**唯一的红线：内部评估绝不能反过来改变整机结论。**
结论永远只看 `results.jsonl` 里有没有 FAIL。内部报告里写满"关注"和"风险"，
只要没有 FAIL，整机就是 PASS —— 那些是给我们排产、挑料、复盘用的，
不是第二套判定标准。`tests/test-internal-report.sh` 里有断言锁着这一条。

**该写什么**归这一节管，**怎么写**归下面第七节管。

## 五、这条规范是有测试守着的

不是靠人记。三处自动守卫，改坏了会跑红：

1. `tests/test-hw-checks.sh` —— 全局扫描 `result_add` 的中文文案和报告生成器里的
   中文串，命中禁词表（`FORBIDDEN` 变量，都是内部实现相关的词）就失败。
   **新写的文案自动受它约束，不需要额外登记。**
2. `tests/test-report-render.sh` —— 真的生成一份客户报告 HTML 再去查，
   确认里面既没有 git commit hash，也没有上面那批词，也没有通电时间，
   **也没有任何采集/压测工具的名字**。
   （在源码里 grep 会被注释里提到的变量名绊倒，所以查生成物。）

   > 查生成物**不只是**为了躲开注释误报，它还是唯一能拦住
   > 「**内容从数据来**」那一路的办法：`metrics.jsonl` 里
   > `mem / 测试工具` 的值就是工具名，源码里根本 grep 不到它。
   > 1.8.4 之前漏出去的那个正是走的这条路。
   > **凡是"内容从数据来"的规则，守卫就必须查生成物。**

   > 但**查生成物时必须先把 `<pre>` 剔掉再扫**（1.9.0 改的）。
   > `<pre>` 里的原始日志按 6-2 是存证、不是结论，允许原样保留 ——
   > 而那些日志本来就是工具自己打的。1.9.0 拿真跑出来的报告量过：
   > `stress-ng` 17 次、`dmidecode` 3 次、`stressapptest` 1 次，**全在 `<pre>` 里**。
   > 也就是说"扫整份 HTML"那个做法**只在测试的 fixture 里恰好没有原始日志时才是绿的**，
   > 换成任何一份真报告都会立刻红，而红的原因和它想守的东西毫无关系。
   >
   > **一条只能在玩具输入上为绿的守卫，和没写没有区别。**
   > 剔掉 `<pre>` 之后剩下的才是我们自己写的东西（判定文案、表格、小节标题），
   > 那里面出现工具名才是真违规；剔干净了也就不必再回避 `fio` 和几个基准程序。
3. `tests/test-internal-report.sh` —— **反过来**确认内部报告里这些字段一个不少。
   内部报告的全部价值就在那几个客户看不到的字段上，少了要能立刻发现。

> 第 1 条曾经是个摆设：它用 `grep -oE 'result_add [^\n]*'` 扫，而 grep 是逐行工作的，
> **只能看到调用的第一行**，可所有长文案都写在反斜杠续行里。于是一句
> 「（需要厂商专用管理工具，本测试盘未包含）」一直大摇大摆地进客户报告。
> 现在先拼续行再扫，并且专门加了一条"守卫必须抓得住违规文案"的自检断言 ——
> **一个从没红过的测试等于没写。**

加新文案时，跑一遍：

```bash
./tests/run-all.sh
```

## 六、写文案的五个自查问题

1. 客户看完这句话，会不会以为**他买的机器**缺了什么/坏了什么？
2. 这句话里提到的东西，客户**有没有可能自己去做**？没有的话为什么要告诉他？
3. 这句话如果被截图发到群里问"这是什么意思"，我解释得清楚吗？
4. **这句话里的每个数字和每个结论，我们真的测到了吗？**（1.8.3 加的）
   ——「交流输入与模块状态均正常」写在一份「交流输入」整列是破折号的报告上；
   「压测结束时温度」写在一台根本没跑硬盘压测的机器上；
   「封装功耗峰值 1034 W」写在一颗 PL1 只有 270 W 的 CPU 上。
   三条都不是判错，是**说得比测得多**。说不出口的就别说，
   读不到的就写"读不到"并说清楚"读不到不代表有问题"。
5. **这句话说的是"这台机器坏了"，还是别的？**（1.9.0 加的）
   三件事在报告里的分量完全不同，措辞不能混：

   | 说的是什么 | 状态 | 措辞要点 |
   |---|---|---|
   | 硬件坏了 | **FAIL** | 说清楚是什么故障、依据是什么 |
   | 配得不对（内存混插、固件版本不一致） | **WARN** | 主语落在**配置**上，写明"不影响机器正常工作" |
   | 跑多快 | **只报数** | 不判、不提"标准"，把测法一并写清楚 |

   **只有第一行能影响整机结论。**别人的验收要求不是我们判机器合格的标准。

   写完回头看一眼：客户读完这句话，会去拆机换件，还是去查插法/BIOS/订单？
   如果答案和你的本意不一样，那就是这句话写错了。

## 七、内部报告的用词规范（1.7.0 起）

上面第二节管的是**客户报告**。内部报告不受那些红线约束（该说的都要说清楚），
但它有自己的一条规矩。

内部这份的定位是**「我们自己复盘用的、更详细的那份数据」**，不是「问题清单」。
它一般不外发，但要按「万一发出去了也站得住」的标准写 —— 客户、供应商、
甚至法务都可能在某个场合看到它。

### 规矩只有一条

**描述「某项数据本轮没有」时，主语是那项数据或它的性质，不是我们。**

| ❌ 现在不写 | ✅ 改成 |
|---|---|
| 盘内没有 storcli64 | 该型号阵列卡的固件版本与逻辑盘状态需由厂商管理工具（storcli64）读取，本轮未加载该工具 |
| 我们这一轮环境的缺口 | 本轮采集范围说明 |
| 缺少 / 未包含 / 精简版 | 本轮未采集 / 本项不适用于该机型 / 该项由厂商工具提供 |
| 某某项没测 | 某某项不在本轮测试范围内（原因：……） |
| 本测试盘 / 盘内…… | （主语换成数据本身，整句重写） |

一律避免「本测试盘」「盘内」「精简」「未包含」这类**主语是我们的否定式表达**。

### 但不许因此丢信息

中性 ≠ 含糊。原因必须**具体、可执行**，工程人员看完要知道下次怎么补齐：

- 是**哪一类**工具（"Broadcom / LSI MegaRAID 系列的厂商管理工具"）
- **哪一项数据**因此没有（"阵列卡的固件版本与逻辑盘状态"）
- 那个工具**到底叫什么**（`storcli64`）—— 这个不能省，省了就没法照着去补
- **怎么补齐**（"放进构建期的 vendor/ 目录"）

「本轮未加载该工具」比「盘内没有 storcli64」信息量并没有变少，只是主语换了。

代码里 `generate_internal.py` 的 `TOOL_PROVIDES` 就是干这个的：
命令名 -> (这项数据是什么, 它由什么提供)。加新工具时同步加一行，
那一节的措辞自动就是对的。

### 这条也是有测试守着的

`tests/test-internal-report.sh` 两头都钉：

- **正面**：`storcli64`、「厂商管理工具」、「阵列卡的固件版本与逻辑盘状态」、
  「本轮未加载该工具」、「补齐办法」，一个都不能少
- **反面**：「盘内没有」「盘内有」「本测试盘」「精简」「我们环境的问题」
  「环境的缺口」「没测」，一个都不许出现

> 那条正面断言是从 1.6.0 的「盘里少带哪个工具，内部要直说」改过来的，
> **意图一个字没变** —— 只是把"直说"从「盘内没有 storcli64」换成了
> 「哪一类工具、哪一项数据因此没有」。改措辞的时候最容易顺手把信息一起删掉，
> 所以这条断言比原来那条还严。
