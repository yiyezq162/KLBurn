# 输出的文档：一次运行到底产出什么

1.10.6 起 PDF 表格使用固定布局与单元格换行，网卡等宽表的全部列须在 A4 内可见。
交付页脚只说明自动实测采集，不披露内部产品名；无独立显卡时不再误称本轮为显卡专项。
内存带宽附注只写实际识别的已占用通道，不声称平台所有通道已经装满。

> 插上盘跑一轮，U 盘的 `out\` 下会多出**一个文件夹**。这份讲清楚：
> 里面每样东西是什么、**哪一样交给客户**、六个测试范围各会得到什么形状的报告。
>
> 规范（哪些内容不许出现在交付报告里、为什么）在
> [`report-policy.md`](report-policy.md)。这份讲的是**形状**，那份讲的是**边界**。

## 一、一次运行产出什么

```
out\20260810_202916_2x-INTEL-XEON-GOLD-6530_512GB_Full\
│
├── 20260810_202916_..._Full.html   ✅ 交付报告（和目录同名）
├── 20260810_202916_..._Full.pdf    ✅ 同一份内容的 PDF
│
├── meta.json                          这一轮的参数：版本、范围、档位、阈值、时间预算
├── results.jsonl                      每条判定一行 —— **整机结论就是从这里算的**
├── metrics.jsonl                      零散实测数值
├── klburn.log                         全程运行日志
├── sys_metrics.csv                    CPU/内存并发阶段与硬盘阶段的系统采样（phase 分列；每 5 秒一采）
├── gpu_metrics.csv                    同上，逐卡（有显卡且跑了显卡压测才有）；20 列，见下
├── SHA256SUMS                         整个目录的校验清单
│
└── raw\                            ❌ 整个目录不外发
    ├── INTERNAL_....html              内部工程报告
    ├── INTERNAL_....pdf
    ├── config-review.txt              现场那一屏配置核对面板的存档
    ├── dmidecode*.txt lspci*.txt ...  采集到的原始输出
    ├── *.json                        只含已验证可解析的 JSON stdout
    ├── *.stderr.txt                  JSON 采集命令的 stderr（有诊断留档）
    ├── *.invalid.txt                 无法解析为 JSON 的 stdout（仅异常时存在）
    ├── smart-pre\  smart-post\        压测前后各一份逐盘 SMART
    ├── counters-pre.txt counters-post.txt   ECC / 热节流 / PCIe AER 前后快照
    ├── bench\                         性能基准的原始日志
    ├── validate\                      专项诊断的原始日志
    ├── stress\                        压测日志 + turbostat 采样
    ├── nic\  raid\  deep\             网卡 / 阵列卡 / 深度留档
    └── ...
```

实测一份完整档：**128 个文件、1.5MB**。

### `sys_metrics.csv` 的阶段口径（1.10.4 起）

`phase=cpu` 是 CPU / 内存并发压测窗口，`phase=disk` 是之后单独进行的硬盘压测窗口。
两段使用同一个采样文件，但报告生成器分别绘图、分别取峰值；硬盘阶段较低的 CPU
频率/功耗不会再接到 CPU 满载曲线末尾，造成“后半程降频”的错觉。

### `gpu_metrics.csv` 的 20 列（1.10.2 起）

压测期间每 5 秒逐卡一行。逐卡查询经过清洗后仍保留各自的换行边界，GPU1..N
不会粘到 GPU0 后面；现场仪表盘和报告曲线都从同一份文件按卡号读取。客户验收单
点名要的那一串监控字段就落在这里，
所以列**只增不改**，位置一旦定下就不动（[§11-73](architecture.md#十一不变量清单改代码前必读)）：

```
1  time          6  clock_sm_mhz   11 pci_bus_id      16 ecc_ue_sram_parity
2  index         7  util_pct       12 serial          17 ecc_ue_sram_secded
3  name          8  mem_used_mb    13 vbios_version   18 ecc_ce_dram
4  temp_c        9  fan_pct        14 util_mem_pct    19 ecc_ue_dram
5  power_w       10 temp_tlimit_c  15 ecc_ce_sram     20 sw_thermal_slowdown
```

采不到的列**留空**，不是 0 —— 消费级卡（5090 这类）没有 ECC，
那五列整片是 `[N/A]`；老驱动没有 `temp_tlimit_c`。
**空和 0 是两件事**，别在读这份 CSV 的时候把空当成 0。

八卡跑满八小时约 46000 行、十几 MB，落在 U 盘的 exFAT 分区上。

### 谁交给客户

| 产物 | 去哪儿 |
|---|---|
| **和目录同名的 `.html` / `.pdf`** | ✅ **随机器交付** |
| 其余全部（含 `raw\` 整个目录） | ❌ 内部留档 |

> **`raw\` 里那份 `INTERNAL_*.html` 放在 `raw\` 里是防手滑**：客户要的是那个
> 和目录同名的文件，`raw\` 整个目录不外发。屏幕上收尾那一屏也会单独黄字提示
> 「engineering copy - do NOT send out」。

> **`SHA256SUMS` 只落文件、不进报告。**用途很具体：半年后客户拿一份报告来问，
> 我们能证明自己归档的那份和他手上那份是不是同一份。客户手上没有 `raw\`，
> 拿到哈希也校验不了什么，印在报告上只会招来"你们是不是怕被改"的提问。

## 二、交付报告的骨架

**五节，顺序固定。**（三、四两节的编号是**动的**——没跑性能基准时压测那节就是"三"。）

| 节 | 回答什么 | 什么时候不出现 |
|---|---|---|
| **一、硬件清单** | 这台机器装了什么 | 永不消失。**全量和「仅导出信息」是八个小节**（1.1 整机 / 1.2 CPU / 1.3 内存 / 1.4 硬盘 / 1.5 阵列卡 / 1.6 网卡 / 1.7 GPU / 1.8 电源），没装的硬件标"未安装"而不是整节消失；**单项专测只出「平台身份 + 被测部件」**，见下面第三节 |
| **二、配置核对** | 装的东西对不对、齐不齐、一不一致 | 一条核对结论都没有、四张表也都不出时整节不出现（只可能发生在单项专测里） |
| **三、性能基准** | 这台机器跑得有多快 | **一条基准结论都没有、也没有逐盘带宽表时整节不出现** |
| **四、压力测试结果** | 扛不扛得住满载 / 压测把什么问题逼出来了 | 永不消失（但"仅导出硬件信息"那一档标题变成「其他检查结论」） |
| **五、原始日志** | 采集到的原文，折叠着 | 永不消失 |

> **一级章节编号是动的**（1.9.8 起）。单项专测里「配置核对」「性能基准」都可能
> 整节不出现，编号写死就会冒出"一、三、四"这种断号。二级编号同理。

### 抬头那几行

```
本轮范围 CPU 专项测试 ｜ 整机序列号 XXXX ｜ 测试时间 … ｜ 测试模式 快速 ｜ 实际耗时 …
报告版本 1.10.5
```

**本轮范围排在最前面**，因为读这份报告的人要回答的第一个问题是
"这台机器测了什么"，不是"它测了多久"。

客户抬头只保留可追溯的报告版本。产品内部名、基础系统、构建时间和源码 commit
保存在 `meta.json` 与内部工程报告，不进入交付正文。GPU 清单遇到“PCI 可见、驱动
未识别”的卡仍会逐张列出；GPU 曲线只连接成功取得的采样点，并给出全部有效卡的
等权平均温度及最高温卡号，不把缺失区间写成“覆盖全程”。

### 结论块

| 形态 | 什么时候 | 含义 |
|---|---|---|
| 绿色 **PASS** | 有判定、且一条 FAIL 都没有 | 本轮**范围内**测过的项目全部通过 |
| 红色 **FAIL** | 有任何一条 FAIL | 不建议出货，下面标红的项就是原因 |
| 红色 **FAIL** + "本报告无效" | **一条判定都没有** | 这轮没跑成，机器**没被评估过**——不是机器坏了，重测 |
| 红色 **FAIL** + "本轮测试未执行" | 选了显卡/硬盘专项，**但这台机器上没有那个部件** | 这一轮作废，**不是机器坏了**，见下 |
| 灰色 **仅硬件信息 · 未做测试** | 范围 = 仅导出硬件信息，且无 FAIL | **这不是通过**，见下 |
| 灰色 **未完成 · 本轮未做该部件老化测试** | 选了某个部件专测，**而那个部件的压测这一轮没跑成**（例如硬盘专测里没人确认破坏性写入），且无 FAIL | **这不是通过**，本报告不能作为该部件的验收依据，见下 |

> ⚠️ **后两种 FAIL 说的是「这一轮作废」，不是「这台机器坏了」。**
> 报告里的措辞是分开的：真故障写「本机存在未通过项，不建议出货」，
> 这两种写的是「本报告无效 / 本轮测试未执行……**这不是硬件故障**」。
> 一台没装显卡的机器本身一点毛病都没有 —— 把它说成"不建议出货"，
> 就是把好机器拦在出货前（一号红线）。

结论块**下面紧跟一句"这一轮覆盖了什么"**——单项专测时会明说
「本轮只对 CPU 做了压力测试与专项验证。内存、硬盘、显卡未做老化测试，
本报告不对这几项的可靠性作出结论。」

> ⚠️ 这一句是**安全项，不是客套**。一个孤零零的绿 PASS 加上这句话，和一个
> 孤零零的绿 PASS，是两份完全不同的报告。半年后翻出来的人靠它分辨这台机器
> 到底测过什么。

### 四种状态

| | 意思 | 影响整机结论吗 |
|---|---|---|
| **PASS** | 测了，没问题 | — |
| **FAIL** | 测了，**这台机器有毛病** | ✅ 整机判 FAIL |
| **WARN** | 有异常读数，但不足以说它坏了（内存混插、少接一路电源线、压测期间热节流） | ❌ 但会在抬头单独列出来"建议出货前确认" |
| **SKIP** | **没测**。这台机器没有这个部件，或者本轮范围不含它 | ❌ |

**整机结论只回答一件事：硬件有没有毛病。** 只看有没有 FAIL。
SKIP 和 WARN 都不拉低结论——但"一条判定都没有"不算通过。

## 三、六个范围各长什么样

下面是拿一台真机（QEMU 里跑的完整档，38 条判定）按各范围**实际会产生的结论行和
原始文件**派生出来的六份报告，骨架是真的：

| 范围 | 一级章节 | 硬件清单出几节 | 和全量比少了什么 |
|---|---|---|---|
| **全量** | 一 硬件清单 / 二 配置核对 / 三 性能基准 / 四 压力测试结果 / 五 原始日志 | 8 | — |
| **CPU 专项** | 同上五节 | 3（整机 / CPU / 内存） | 性能基准里只剩 CPU 那条；压测节只有 CPU 相关 |
| **内存专项** | 同上五节 | 3（整机 / CPU / 内存） | 同理，只剩内存带宽 |
| **显卡专项** | 同上五节 | 4（+ GPU） | 性能基准里是显卡带宽；压测节是显卡相关 |
| **硬盘专项** | 同上五节 | 5（+ 硬盘、阵列卡） | 性能基准里是硬盘带宽；压测节是硬盘相关 |
| **仅导出信息** | 一 / 二 / 三 性能基准 / **四 其他检查结论** / 五 原始日志 | 8 | 没有任何压测，所以第四节改叫「其他检查结论」，也没有压测时长表和曲线 |

### 单项专测：照采不照报（1.9.8）

**单项专测是一把独立的工具，不是"全量报告删掉几行"。** 拿去测硬盘的人要的是
一份硬盘测试单，上面写清楚这是哪台机器就够了 —— 不需要知道这台机器插了什么
网卡、什么显卡、PCIe 链路跑到了几档。

所以交付报告只出「**平台身份（整机 / CPU / 内存）+ 本轮被测的那个部件**」：

- 平台身份那三节里，**不是被测部件的那个给简版**：CPU 只留型号 / 路数那张表
  （不列逐路频率、缓存、虚拟化），内存只留装机容量 / 条数（不列逐条明细）。
- 网卡、GPU、电源那三节，以及「平台关键设置」「核对依据的实测值」
  「固件版本清单」三张表，只进全量和「仅导出信息」。
- 「原始日志」也跟着裁：一份硬盘测试单上不会再附整机 IPMI 传感器读数，
  也不会附那份四十万字符的 dmidecode 原文。

⚠️ **`raw/`、`results.jsonl` 和内部工程报告一个字都不少**，裁的只是交付那一份。

⚠️⚠️ **只藏 PASS / SKIP，WARN 和 FAIL 一条都不许藏。** 只压了 CPU 的那一轮里
PCIe 报了新增 AER、BMC 记了电源掉电，那仍然是**这台机器**的毛病，
和压了哪个部件无关。范围裁掉的是"没话说的行"和整块的清单表格，
不是"这台机器有什么毛病"。

几条值得单独说的：

- **编号永远不断号。** 裁掉小节之后 3.1、3.2 会重新连上，不会出现 3.1 之后直接跳 3.3。
  （这一条有断言钉着——断号是这一类改动最典型的翻车。）
- **范围外的压测时长不印"0 秒"。** 只测 CPU 的那一轮里印一行「内存压测时长 0秒」，
  读的人第一反应是"内存压测失败了"，而这一轮压根没打算测它。
- **范围内的那个部件反过来写得更细**：CPU 专测多一节「逐颗 CPU 满载温度」、
  内存专测多一节「逐条内存 ECC 计数（压测前后对比）」、显卡专测多两条逐卡
  频率/风扇曲线、硬盘专测多一节「逐盘 SMART 关键项（压测前后对比）」。

  > 这几节**数据不在就整节不画**（老机器没有 EDAC、虚拟机读不到逐颗封装温度），
  > 不铺一屏"—"。所以在 QEMU 上看不到它们是正常的。

- **加细不等于放宽红线。** 通电时间、累计写入量、磨损百分比这类寿命字段，
  在**任何**范围下都不进交付报告——哪怕这一轮就是硬盘专项测试。

### 选了某个部件专测，但这台机器上没有那个部件

现场手滑、或者拿错机器：选了 `[4]` 显卡专项，插的却是一台没有独立显卡的机器；
选了 `[5]` 硬盘专项，而机器上的盘全都在使用中。

**这一轮一项测试都跑不成，所以流程直接跳出**：屏幕上打一块红色大框说明原因，
不再往下走（不问擦盘、不跑基准、不压测、不复查，连配置核对那一屏也跳过），
直接出报告，**整机结论判 FAIL**。

> ⚠️ **这个 FAIL 的含义是「这一轮作废」，不是「这台机器坏了」。**
> 没装显卡的机器本身一点毛病都没有。所以报告里那句话是
> 「本轮测试未执行：所选的测试范围在本机上没有可测的部件。**这不是硬件故障** ——
> 请确认是不是选错了测试范围、或者测错了机器」，
> **绝不会**写成「本机存在未通过项，不建议出货」。
>
> 1.9.6 及之前这种情况打的是**绿色 PASS**，下面还写着"本轮只对显卡做了压力测试
> 与专项诊断"—— 而它一项都没做。**把"没测"包装成"通过"，比不做这个功能还糟。**

**只有显卡和硬盘两档会这样。** CPU 和内存不做这个判断 —— 没有这两样机器
根本开不了机，"选了 CPU 专测却没有 CPU"这件事不存在。

### 选了某个部件专测，那个部件却没真压过（1.9.8）

部件在机器上，但那一项压测这一轮没跑成。最常见的是硬盘：破坏性写入确认
等了 120 秒无人应答，按默认跳过 —— 1.9.7 现场真跑出来一份**绿色大 PASS**
加一行「硬盘专项测试」，下面还写着"本轮只对硬盘做了压力测试与 SMART 复查"，
而那台机器的硬盘一个字节都没压过。

现在结论块换成灰色的「**未完成 · 本轮未做该部件老化测试**」，并明说
**本报告不能作为该部件的验收依据**、**这不是硬件故障**，
把跳过的原因原样带出来。已采集到的硬件信息与检查结论照常有效。

> 和上面那条、和「仅导出硬件信息」是同一类：**把"没测"包装成"通过"**，
> 比不做这个功能还糟。FAIL 照打不误，真跑了压测的那一轮照常绿。

### 「仅导出硬件信息」那一档

**这一档不出 PASS 大字**，屏幕上是中性的青色 `INFO` 加一句
"This is NOT a pass"，报告里是灰色的「仅硬件信息 · 未做测试」，
并写明**不能作为出厂验收依据**。

理由很直接：那一轮一个压测都没跑、一个部件都没验过，报告里没有任何东西
支持"合格"这个结论。**把"没测"包装成"通过"，比不做这个功能还糟。**

FAIL 照打不误——那一档里 FAIL 的来源是采集或配置核对真的判出了问题
（内存容量对不上、看到虚拟设备），那是实打实的、必须看见的东西。

## 四、内部工程报告（`raw\INTERNAL_*.html`）

**不交付。**它比交付报告详细得多，写给我们自己：

| 类别 | 例子 |
|---|---|
| 不参与判定的字段 | 通电时间、通电次数、SSD 已用寿命、异常掉电次数 |
| 我们这一轮环境的缺口 | 盘里没带某个工具、某条采集命令超时了、没能联网校时 |
| 版本可追溯 | KLBurn 版本、**源码 commit（含 dirty 标记）**、构建日期、驱动版本、**这一轮算力是拿哪套程序量的** |
| 二次解读 | 逐颗 CPU 温差、内存混插、插槽利用率、PCIe 链路降级、光模块收发光功率 |
| 主观评价 | 分 良好 / 关注 / 风险 / 记录 四级 |

**唯一的红线：内部评估绝不能反过来改变整机结论。** 结论永远只看
`results.jsonl` 里有没有 FAIL。内部报告里写满"关注"和"风险"，只要没有 FAIL，
整机就是 PASS——那些是给我们排产、挑料、复盘用的，不是第二套判定标准。

## 五、一批机器：仓库侧的两个工具

这两个**不进盘**，在拷回来的一堆 run-dir 上跑。

### `tools/klburn-summary.py` —— 一批一张表

```bash
python3 tools/klburn-summary.py out/ -o summary.csv
```

一台机器一行的 CSV（`utf-8-sig`，Windows 上双击 Excel 不乱码）。
**它只把 `results.jsonl` 摊平，不做任何新判定**，整机结论和盘里、和两份报告
同一个口径。

⚠️ **非全量的那几台，结论列写成 `PASS(CPU)` 这种形状，而不是光秃秃的 `PASS`。**
一台只跑了 CPU 专测的机器，`results.jsonl` 里当然没有 FAIL——可它的内存、
硬盘、显卡**根本没测过**。而这张表正是拿来做"这一批能不能出货"这个决定的：
一列全是 PASS 的表格里混进这么一台，没有任何人会发现。
所以它排序筛选时和 `PASS` 不是同一个值，范围另外单独占一列，
屏幕上还会单独报一句"本批有几台不是全量测的"。

### `tools/klburn-diff.py` —— 两台对比

```bash
python3 tools/klburn-diff.py <A的run-dir> <B的run-dir>
```

**只报差异，不判合格，也不碰性能数字**（那些本来就机器与机器之间有差别）。
用途是"同一批为什么这台不一样"。

## 六、常见问题

**Q：我这份报告里没有「性能基准」那一节。**
那一节是有条件的：一条基准结论都没有、也没有逐盘带宽表时整节不出现。
一节全是 SKIP 的"基准"只会招来"你们是不是没测"的提问。
盘里没放对应的基准程序、或者本轮范围不含它，都会这样。

**Q：为什么硬盘相关的项目全不见了？**
现场没确认破坏性写入时，硬盘压测那几项（含 SMART 复查）整个不显示——
那是操作员当场自己选的，留一行「SKIP 现场选择跳过」只会让客户以为我们少测了。
**盘的清单、序列号、固件、容量、SMART 健康状态照常都在**，藏的是"压测"，不是"硬盘"。
真跑了就原样都回来。而 SMART 复查判 **FAIL** 时**一定显示**——那是实打实的坏道。

**Q：报告里为什么没写"合格 / 不合格的标准是多少"？**
**性能数字只报不判。** 这张盘插上就跑、无人值守，现场没有人、也没有地方去填
"这台机器该达到多少"。凭空写一个数进来，等于我们替客户定了一个他没定过的标准。
**谁做验收，谁拿自己的标准去对我们报出来的实测值。**

**Q：一台机器测了两次，会覆盖吗？**
不会。目录名带日期时间；万一 RTC 卡住导致同名（纽扣电池没电的机器上是必然），
会自动在末尾加 `_01` `_02`，前一次的报告一个字都不动。

**Q：报告能离线看吗？**
能。HTML 是自包含的（CSS 内嵌、图表是手写 SVG、logo 是 base64），
不依赖任何外网资源，Windows 上双击就能看。
