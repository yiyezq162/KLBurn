# KLBurn — 服务器出厂老化测试 U 盘

一根 U 盘插上服务器，开机自动跑完整套出厂测试，报告直接落到 U 盘里，
拔下来插 Windows 电脑双击就能看。

**一个盘通吃所有机型**：无显卡的通用服务器、带阵列卡的存储机、多卡 GPU 服务器。
没有的硬件自动跳过并在报告里标注，不会卡住，也不会误判为故障。

**不需要网络也能完整跑完**。接了网线的话会顺手联网校时、测一下网口连不连得通，
纯属加分项，不接网线不影响任何判定。

```
插盘 → 开机 → 选时长（30秒倒计时，不按就用默认）→ 走开
                                                    ↓
        U 盘里多出一个文件夹：报告 + 全部原始数据 ← PASS / FAIL 大字
```

## 四样产物，只有一样交给客户

| 产物 | 是什么 | 去哪儿 |
|---|---|---|
| **ISO 测试盘** | `out/KLBurn-*.iso` | 内部，发货前测试用 |
| **工程目录** | `raw/`、`meta.json`、`results.jsonl`、`klburn.log`、各种 `.csv` | 内部留档，日后回档追溯 |
| **工程数据报告** | `raw/INTERNAL_*.html` + 同名 `.pdf` | 内部，复盘用 |
| **`报告名.html`** | 自包含的中文报告 | ✅ **随机器交付** |
| **`报告名.pdf`** | 同一份内容的 PDF，转发/归档用 | ✅ **随机器交付** |

两份 HTML 是一份数据的两种视角：

|  | 交付报告 | 工程数据报告 |
|---|---|---|
| 读者 | 客户的采购 / 运维 | 我们自己 |
| 回答 | 这台机器合不合格 | 这台机器什么成色、这一轮测得干不干净 |
| 位置 | 报告目录下与目录同名的 `.html` | `raw/INTERNAL_<机器名>.html` |
| 内容 | 硬件清单 + 每项结论 + 温度功耗曲线 | 上面全都有，另加设备台账字段、逐颗 CPU 温差、光模块收发光功率、本次采集的缺口、源码版本、raw/ 全文件索引 |

交付报告只放**参与判定、或者支撑判定**的内容 —— 一块盘几百行 SMART 属性，
绝大部分和"合不合格"无关，都塞进去只会把报告撑成一堆看不懂的数字。
其余参数完整留在工程数据里，做设备台账和日后回查用。

工程报告放在 `raw/` 里、文件名带 `INTERNAL_` 前缀，取报告时不容易拿错。

**文案规范见 [`docs/report-policy.md`](docs/report-policy.md)，有三处自动化守卫在
`tests/` 里盯着，写出跑偏的文案会直接跑红。**

## 它测什么

### 1. 硬件信息采集

- **主板 / BIOS / 每颗 CPU / 每根内存条**的厂商、颗粒型号、序列号，
  并核对装机容量和系统实际识别到的容量是否一致（缺条 / 开了内存镜像会在这里被抓到）
- **每块盘**：型号、固件、容量、SMART 健康状态。
  **阵列卡后面的物理盘也逐块读**——RAID 模式下操作系统只看得到逻辑盘，
  物理盘没有盘符，这些盘的 SMART 是通过阵列卡透传取的
- **阵列卡**：型号 / 固件（只采集，不压测）
- **网卡**：型号 / 驱动 / 固件 / 协商速率；DHCP 取地址 + ping 网关做连通性测试
- **电源**：核对每一路有没有交流输入（配合 BMC 传感器读数，比 DMI 报的状态更准）
- **显卡**：`nvidia-smi -q` 全量
- **IPMI 传感器读数 + SEL 事件日志**
- **PCIe 链路**：额定 vs 实际协商的速率和宽度（x16 的卡插在 x8 槽上，机器照样跑，性能砍一半）
- **只留档、不参与判定的一批**（进内部报告，给设备台账和日后回查用）：
  各部件固件版本清单（`fwupdmgr`）、交换机侧邻居（LLDP，**只收不发**）、
  CPU 逐核频率/能耗实测（`turbostat`）、NVMe 厂商私有 SMART、
  背板/机箱状态（`sg_ses`）、网卡固件详情（`mstflint`）

### 2. 压力测试

开机菜单选时长，六个档位，30 秒倒计时默认标准：

| 档位 | 时长 | 用在哪 |
|---|---|---|
| QUICK 快速 | 10 分钟 | 确认主链路通不通，新盘第一次跑 |
| **STANDARD 标准** | **30 分钟** | **默认**，常规出货抽测 |
| EXTENDED 加长 | 1 小时 | 单台复测、可疑机器 |
| LONG 长测 | 2 小时 | 完整老化 |
| SOAK 深度 | 4 小时 | 重点机型、批次首台 |
| ENDURANCE 耐久 | 8 小时 | 过夜跑，下班前插上第二天来看 |

压测项目：

| 项目 | 工具 | 说明 |
|---|---|---|
| CPU | `stress-ng` 全核 | 同时每 5 秒记录温度、频率、封装功耗 |
| 内存 | `stressapptest` | 吃掉可用内存减去安全余量的部分，校验数据错误 |
| GPU | `gpu_burn` | 满载，每 5 秒记录逐卡温度/功耗/频率 |
| 硬盘 | `fio` 裸盘读写 | **破坏性操作，需现场两道确认，默认跳过** |

**CPU / 内存 / GPU 三项并发压测**：选多长就真的测多长，互不占用彼此的时间——
选 10 分钟，CPU 就是满载 10 分钟，不会因为还要陪跑内存/GPU 而被腰斩。

硬盘单独测（fio 裸盘读写要是跟 CPU/内存满载凑一起，带宽/IOPS 数字会被 CPU 争用扭曲），
额外占所选时长的 30%，不从前三项里扣 —— 也就是说选 2 小时、又确认了硬盘压测的话，
压测部分一共 2 小时 36 分钟。不确认硬盘压测（默认）就等于所选时长。

> **跳过硬盘压测时，客户报告里不会出现和它相关的任何字段**（1.7.6 起）——
> 那一项、SMART 复查、「本次压测」列、「硬盘压测时长」全部不显示。
> 现场绝大多数机器都不做这项（客户不让往盘里写），报告上留一行
> 「SKIP 现场选择跳过」，客户看到的是"少测了一项"，而那是他自己选的。
> **盘的清单、序列号、固件、容量、SMART 健康状态照常都在** —— 藏的是"压测"，
> 不是"硬盘"。真跑了就原样都回来。
>
> 但 SMART 复查判 **FAIL**（这一轮新增了坏道）时**一定会显示** ——
> 那是实打实的硬件问题，和跑没跑压测无关。规范见
> [`docs/report-policy.md`](docs/report-policy.md) 二-4。

### 3. 测后复查

**这一步才是出厂测试真正的价值** —— 压测跑完不代表没问题，要看压测把什么逼出来了：

- 对比**测前 / 测后** SMART：有没有新增坏道、CRC 错误、NVMe 介质错误
- 扫 `dmesg` 找 MCE / EDAC / PCIe AER / I/O error 等硬件级错误
- 对比 BMC SEL，看压测期间有没有新增告警事件
- 温度是否超阈值
- **内存 ECC 计数**：可纠正错误（CE）涨了判 WARN，不可纠正（UE）涨了判 FAIL ——
  UE 意味着数据已经错了，这种机器不能出厂
- **CPU 热节流计数**：压测期间真降频了判 WARN（散热或风扇策略的问题，不是 CPU 坏）
- **PCIe AER 计数**：可纠正的判 WARN，不可纠正的判 FAIL

> 这三条判的都是**差值**（测后 − 测前），不是绝对值。二手机器和返修件带着历史计数
> 很正常，按绝对值判会把它们全判成故障。数据直接从内核 sysfs 读
> （`/sys/devices/system/edac/`、`thermal_throttle/`、`aer_dev_*`），
> 不依赖 `ras-mc-ctl` / `edac-utils` 装没装。读不到一律 SKIP，绝不判 FAIL。

## 报告长什么样

自包含的 HTML（内嵌 CSS + 手写 SVG 图表，**不依赖任何外网资源**，
拷到没网的电脑上照样正常显示）：

- **① 硬件清单** —— 这台机器装了什么，有啥列啥，没有的标"未安装"
- **② 压力测试结果** —— 每项 PASS / FAIL 大字标注 + 详细数据 + 温度功耗曲线图
- **③ 原始日志** —— 可折叠，全部保留

报告写到 U 盘根目录的 `out\` 文件夹（不存在会自动创建），**每次测试单独一个文件夹**：

```
<U盘根>\out\
    20260731_101500_2x-Intel-Xeon-Gold-6530_512GB\      ← 每次测试一个文件夹
        20260731_101500_2x-Intel-Xeon-Gold-6530_512GB.html   ← 双击这个看报告
        20260731_101500_2x-Intel-Xeon-Gold-6530_512GB.pdf    ← 同一份内容，转发给客户用这个
        klburn.log  results.jsonl  meta.json  sys_metrics.csv
        raw\
            INTERNAL_20260731_101500_....html            ← 内部详细版，别发出去
            INTERNAL_20260731_101500_....pdf             ← 同上，也别发出去
            dmidecode.txt  smart-pre\  smart-post\  deep\  ...
    20260731_143052_Intel-Xeon-Silver-4310_128GB\       ← 另一台机器，互不影响
```

命名格式 **`日期_时间_CPU型号_内存容量`**，多路机器 CPU 前带路数（`2x-`），
整机序列号在报告内容的抬头里。

## 几个不太一样的地方

这些是踩了现场的坑之后才长成现在这样的，也是这个项目和"随便跑个 stress"的区别。

**① 四态判定，绝不把"没有"说成"坏了"**
所有项目的状态是 PASS / FAIL / SKIP / WARN 四态。没装阵列卡、没装显卡、没接网线
一律 SKIP，不影响整机结论；**有卡但认不到**才是 FAIL。
整机结论只看有没有 FAIL —— 但**一条判定都没有也不算通过**：那说明这轮压根没跑成，
报告会明确写「本次测试未产生任何判定结果，本报告无效」，而不是打一个绿色 PASS。

**② 测试环境自己的问题，绝不算到客户机器头上**
内存压测被 OOM killer 打死 → 判 WARN 并写明"这是测试环境的容量限制，不是内存故障"。
显卡驱动版本不支持客户的新卡 → 判 SKIP 说"驱动与显卡不匹配"，
而不是把好卡说成"显卡、供电或插槽异常"。
**把好机器拦在出货前，比漏判更糟。**

**③ 阵列卡后面的盘也要真查到**
RAID 模式下 `/dev/sdX` 是逻辑盘，物理盘根本不在 `/dev` 下 —— 直接读 SMART
读到的是逻辑盘，没有任何属性。这意味着"测前测后 SMART 对比"在带阵列卡的机器上
会**整项空跑**：报告写着 PASS，实际一块物理盘都没查过。现在会自动认出阵列卡，
逐块透传读取，物理盘的型号/序列号/温度和坏道增长照常进报告和判定。

**④ 日志判读一律抠数字，不做关键字匹配**
`stressapptest` / `stress-ng` / `gpu_burn` 正常跑完的日志里本来就带
`Found 0 hardware incidents`、`errors: 0`、`failed: 0` 这些字样。
早期版本用 `grep -q` 判定，结果是**每一台好机器都被判 FAIL**。

**⑤ U 盘自己绝不会被写穿**
fio 的目标盘要过五道排除。Ventoy 场景下 udev 被禁、`lsblk` 完全看不见它的 dm 设备，
所以反查走的是 `/sys/dev/block/<主:次>` 设备号，不依赖任何 `/dev` 下的名字。
`tests/test-disk-exclusion.sh` 用 loop + dm-linear 搭出同构设备链专门锁这条路径。

**⑥ 破坏性写入要连过两关**
原样打出 `yes` 回车（打错、直接回车、120 秒超时一律跳过）→
最终警告面板再列一遍要被擦除的盘，按 `y` 才真的开始（60 秒超时跳过）。
跳过记 SKIP，不算 FAIL。

**⑦ 报告落盘有四层回退**
卷标 → 同一根 U 盘的 exFAT 分区 → 任意可移动盘的 exFAT → dm 映射设备。
四层都找不到才落 `/tmp`，并在屏幕上打黄色大框警告。

**⑧ gpu_burn 是静态链接的自包含二进制，而且带全了每一代的 cubin**
CUDA 运行时库不在显卡驱动里，直接打包动态链接的版本一跑就是
`error while loading shared libraries`，然后被判成"显卡故障"。
用 `nvprune` 裁剪静态库再静态链接，330MB 出头，装完还用 `ldd` 自检。

裁剪时**只带一代 cubin 的坑更隐蔽**：`nvprune --arch` 写多次不叠加（后面的顶掉前面的），
1.6.0 及以前出的盘实际只带了一代，别的卡上 cuBLAS 找不到可用核、非零退出，
照样被判成"显卡故障"。1.7.1 改成 `-gencode` 并把 Pascal 到 Blackwell
（`sm_60/61/70/75/80/86/89/90/100/120`）全带上 —— **2017 年以后的 N 卡都覆盖**，
30/40/50 系和 T4 / A100 / H100 / H200 这些推理卡都在内。
构建期逐代自检：拿每一代单独裁一次，比对裁剪前后的体积，少一代直接构建失败。

**⑨ 屏幕是给人看的，不是滚动的日志**
每一块整屏页面开头都是绿色的 ASCII 大字标题 + 当前页名（配置核对、压测仪表盘、
硬盘视角、破坏性写确认、时长菜单、最终结论）—— 现场那块屏经常被拍照发群里。
青色框线分区、绿黄红按温度、黄色标出"会被擦掉的盘"。

**颜色只加在边框层，绝不进内容串。** 这不是风格问题，是算宽度的问题：列宽全靠
`printf '%-*.*s'` 补齐，而它数的是**字符个数** —— 颜色码混进内容串，那几个转义
字节会被算成可见字符，补出来的行短一截，整屏重绘立刻错位、越刷越花。
核心断言只有一条，但它管住了全部：**把颜色码去掉之后，必须和不上色时一字不差。**
颜色整体可关（`PANEL_COLOR=0`，或 stdout 不是 tty 时自动置空），
写进 `raw/config-review.txt` 的存档就是关掉生成的。

**⑩ 911 项回归测试，全都不需要真实硬件**
跑全套的同时还会过一遍 shellcheck。

```bash
./tests/run-all.sh
```

**变异验证是脚本，不是一次性人工活。** 把每个已修复的 bug 逐个塞回代码里，
确认对应的用例真的会跑红 —— 一个从没红过的测试等于没写：

```bash
./tests/mutate.sh
```

**出好的盘会在 QEMU 里真的开机跑一遍**，报告从虚拟"U 盘"里挖出来验。
全程按**日志锚点**走（宿主机直接 grep 那个虚拟 U 盘镜像就能看到虚拟机写的日志），
一次盲发按键都没有 —— 按错方向就是真擦盘：

```bash
sudo ./tests/e2e-qemu.sh --stage full          # 完整跑一遍 QUICK 档
sudo ./tests/e2e-qemu.sh --stage full --disk-stress   # 再加上"fio 真写盘"
```

**构建完还要跑一条固件对账**（几秒）。它守的是「盘里关键驱动要的固件一个都不能少」——
少了不会有任何报错，驱动起不来，`ip link` 里那块网卡就是不存在，
**报告写着这台四口机器没网卡**：

```bash
./tests/check-firmware.sh
```

## 快速上手

```bash
# 1. WSL 里装构建依赖（只需一次）
sudo apt-get update
sudo apt-get install -y xorriso squashfs-tools rsync curl ca-certificates \
                        gdisk fdisk file zstd python3 jq dosfstools mtools

# 2. 改抬头（可选）：build/config.sh 里的 COMPANY_NAME

# 3. 构建（第一次会自动下载约 3GB 的 Ubuntu 源 ISO）
cd /mnt/c/Users/li/Desktop/project/KLBurn
sudo ./build/build-iso.sh

# 4. 产物在 out/ 目录，用 Rufus 写盘
#    详细步骤见 docs/usb-rufus.md
```

### 关于构建目录（重要）

构建工作区默认在 **`~/klburn-build`**，也就是 WSL 的原生文件系统。

**绝对不要把它设到 `/mnt/c` 下面。** `/mnt/c` 走 9p 协议，解 squashfs 要写几十万个
小文件，性能会差到不可用（几分钟的活干几小时）。构建脚本里有硬性检查，
检测到 `/mnt/*` 会直接拒绝执行。要换位置用 `export KLBURN_WORK=$HOME/somewhere-else`。

源码本身放在 `/mnt/c` 下没问题（只是读几十个小文件）。
构建产物 ISO 最后会自动拷回项目的 `out/` 目录。

大约需要 **12 GB** 磁盘空间（源 ISO 缓存 3.2G + 解包 3.2G + 根文件系统 2.5G +
临时 1.5G + 输出 ~1.5G）。

## 构建 ISO

```bash
sudo ./build/build-iso.sh
```

第一次跑会自动从清华镜像下载 `ubuntu-24.04.4-live-server-amd64.iso`（约 3.2 GB，
支持断点续传，中断了重跑就继续）。之后的构建复用缓存。
耗时：首次约 10~15 分钟（不含下载），之后增量构建约 5~8 分钟。

### 常用参数

```bash
sudo ./build/build-iso.sh                    # 常规构建
sudo ./build/build-iso.sh --without-nvidia   # 出一张不含显卡驱动的盘
sudo ./build/build-iso.sh --rebuild-fs       # 强制重新解 squashfs（换了源 ISO 时用）
sudo ./build/build-iso.sh --clean            # 清空工作区从头来（保留已下载的源 ISO）
sudo ./build/build-iso.sh --iso /path/to.iso # 用指定的源 ISO
sudo ./build/build-iso.sh --skip-download    # 源 ISO 不存在就报错，不去下载
```

### vendor/ 里放什么

`vendor/` 目录不进版本库（体积大、有授权限制），需要手动放进去。
构建脚本自动检测，**放了就带上，没放就跳过对应功能，不会报错中断**：

| 放什么 | 不放会怎样 |
|---|---|
| `vendor/nvidia/NVIDIA-Linux-x86_64-*.run` | 出一张不含显卡驱动的盘 |
| `vendor/gpu_burn/{gpu_burn,compare.fatbin}` | 显卡信息照常采集，但不做满载压测 |
| `vendor/storcli/storcli64` | 阵列卡只能报 PCI 型号，读不到固件版本和逻辑盘状态（**卡后面物理盘的 SMART 不受影响**，那条路不依赖它） |
| `vendor/{perccli,ssacli,sas3ircu}/` | 同上，分别对应 Dell PERC / HPE Smart Array / IT 模式 HBA。一张卡只有对得上的那个工具认得，放几个算几个 |
| `vendor/logo.png` | 报告抬头不显示 logo |

详见 [`vendor/README.md`](vendor/README.md)。gpu_burn 需要自己编译一次：

```bash
./build/build-gpu-burn.sh        # 不需要 root，也不需要机器上真有 N 卡
```

## 制作 U 盘

**详细图文步骤见 [`docs/usb-rufus.md`](docs/usb-rufus.md)。** 简要版：

1. Rufus 写 ISO，**必须选「DD 映像模式」**（不是 ISO 模式）
2. 磁盘管理 / `diskpart` 在剩余空间建一个 **exFAT** 分区，卷标 **`KLBURN`**（大写）
3. 插服务器，BIOS 选 U 盘启动

> 如果你会经常改脚本重新出盘，`docs/usb-rufus.md` 末尾有个 **Ventoy 方案**，
> 换版本只要替换 ISO 文件，不用重新写盘和重建分区，省事很多。已完整验证过。

## 现场怎么用

1. 插 U 盘，开机，BIOS 启动菜单选 U 盘（常见按键 `F11` / `F7` / `Esc` / `F12`）
2. GRUB 菜单 5 秒后自动进入
3. 系统起来后自动进入测试，**首先显示报告存储位置**：
   - 绿色 `Data partition: /dev/sdb2 -> /mnt/klburn-data` = 正常
   - 黄色大框警告 = 没找到 U 盘数据分区，报告只会写到 `/tmp`，关机就没了
4. **尝试联网校时**（几秒到几十秒，接了网线才会有动作）
5. **选测试时长**：30 秒倒计时，不按键默认标准（30 分钟）
6. 自动采集硬件信息
7. **配置核对面板** —— 采集完先把「这台机器到底装了什么」摆出来，让现场对一遍：

   ```
     _  ___     ____
    | |/ / |   |  _ \ _   _ _ __ _ __
    | ' /| |   | |_) | | | | '__| '_ \
    | . \| |___|  _ <| |_| | |  | | | |
    |_|\_\_____|_| \_\\__,_|_|  |_| |_|
    Server Factory Burn-in Test   v1.8.4                       2026-08-02 14:33:07
   +==============================================================================+
   |                             CONFIGURATION REVIEW                             |
   +==============================================================================+
   |  SYSTEM                                                                      |
   |    Manufacturer  Dell Inc.                  Product   PowerEdge R750         |
   |    Serial        ABC1234                    BIOS      2.10.2 (2025-03-11)    |
   +------------------------------------------------------------------------------+
   |  CPU                                                                         |
   |    2 x Intel Xeon Gold 6430  32C/64T        Total 128 logical CPUs           |
   +------------------------------------------------------------------------------+
   |  STORAGE                                                                     |
   |    /dev/nvme0n1   1.6TB  SAMSUNG MZQL21T9HCJR   SN S6CVNE0T   [TESTABLE]     |
   |    /dev/sda     446.6GB  DELLBOSS VD                          [MOUNTED]      |
   +==============================================================================+
         Review the configuration above.  Press any key to continue.   [58s]
   ```

   **60 秒倒计时，按任意键立即继续，超时自动继续** —— 这一屏绝不会卡住流程。
   少一条内存、少一张网卡、少一块盘，在这里就能发现，不用等三十分钟压测跑完。
   哪一项没有就整块不画（没显卡就没有 GPU 那块）。

   `[TESTABLE]` 是黄的、`[MOUNTED]`/`[TEST MEDIA]` 是绿的 —— **下一屏就是破坏性写
   确认**，"哪几块盘会被 fio 擦掉"这一眼很值钱。
8. **硬盘压测确认（默认跳过）** —— 硬盘的型号 / 容量 / 序列号 / SMART 健康状态
   在这一步之前就已经采集完了，报告里一定有。这里问的只是要不要额外做**破坏性的**读写压测
9. **CPU / 内存 /（GPU）并发跑满全部选定时长**，屏幕是一块每 2 秒整屏重绘的仪表盘：
   逐颗 CPU 一行（型号 / 频率 / 温度 / 占用率）、逐张显卡一行
   （型号 / 显存 / 温度 / 功耗 / 利用率），内存和网口各一行汇总，进度条在最底下。

   ```
     _  ___     ____
    | |/ / |   |  _ \ _   _ _ __ _ __
    | ' /| |   | |_) | | | | '__| '_ \
    | . \| |___|  _ <| |_| | |  | | | |
    |_|\_\_____|_| \_\\__,_|_|  |_| |_|
    Server Factory Burn-in Test   v1.8.4                                     QUICK
   +==============================================================================+
   |                         BURN-IN  CPU + MEMORY + GPU                          |
   +==============================================================================+
   |  CPU     MODEL                              FREQ      TEMP    BUSY           |
   |   #0     Intel Xeon Gold 6430              3100 MHz     67 C   100%          |
   |   #1     Intel Xeon Gold 6430              3090 MHz     65 C    99%          |
   +------------------------------------------------------------------------------+
   |  MEMORY   Used   492 / 512 GB              ECC  CE 0 / UE 0                  |
   |  NETWORK  4 ports, 2 up                                                      |
   +------------------------------------------------------------------------------+
   |  GPU   MODEL                       MEMORY            TEMP   POWER   UTIL     |
   |   0    NVIDIA H200 PCIe            138.2/141.0 GB     71 C    598 W   100%   |
   +==============================================================================+
   |  ELAPSED 00:04:12   REMAINING 00:05:48                                       |
   |  [########################............................]  42%                 |
   +==============================================================================+
   ```

   CPU / 显卡 / 硬盘那几行**按判定用的那两条温度线上色**（绿 → 黄 → 红），
   阈值在 `klburn.conf` 里改了颜色跟着变；读不到温度就不上色 ——
   读不到既不是"正常"也不是"异常"，不该给任何暗示。

   框线全是 ASCII（`+ - | =`），因为现场多半是通过 BMC 的 KVM 或串口看的，
   字体和字符集都不受我们控制 —— Unicode 制表符有很大概率变成一屏乱码。
10. 硬盘单独测（如果确认了）—— 屏幕换成硬盘视角：逐盘的读写带宽、IOPS、温度
11. 测后复查 → 生成两份报告 → **PASS / FAIL 大字**，下面跟一份逐项结果
    （FAIL 红、WARN 黄、SKIP 灰、PASS 绿 —— 二十几行状态，黑白一片时要逐行找）
12. 收尾菜单：`r` 重启 / `p` 关机 / `s` 进 shell 排查 / `t` 再测一遍 /
    `c` 清 BMC 事件日志

> **`c` 清 BMC 事件日志（SEL）**：机器拷完机之后，BMC 里常压着一堆装机阶段的
> 报错（拔插硬盘、电源没插好、反复上下电），跟出厂后的状态没关系，
> 留着只会让客户开机一看 SEL 全是红的。要原样打 `yes` 才执行。
>
> **只清事件日志，不动任何设置** —— 网络配置、用户、传感器阈值、启动项
> 一概不碰。另外要知道：IPMI 标准里能清的只有 SEL 这一个，
> 有些厂商 BMC 另有独立的审计日志/操作日志，那些得进 BMC 网页界面清，
> 这里够不着。
>
> 它**故意不进自动流程**：SEL 正是「BMC 事件日志复查」那一项的判定依据，
> 自动清就等于把自己的证据先销毁掉。所以要等报告出完再手动点。

按 `Alt+F2` 可以切到另一个控制台，root 免密登录，用来手工排查。

> 屏幕上的提示都是英文——Linux 文本控制台默认显示不了中文（会变方块）。
> **报告（U 盘里那个 `.html` 文件）是全中文的**，不受影响。

## 换成别家的抬头

抬头在**构建时**钉进 ISO，现场运行时绝不会问操作员 —— 一根盘做出来是谁的抬头就是谁的。
报告生成器里没有任何写死的公司名。

改 [`build/config.sh`](build/config.sh) 顶部的「品牌抬头」一块：

```bash
COMPANY_NAME="广州市鲲林科技有限公司"      # 报告抬头
REPORT_TITLE="服务器出厂老化测试报告"       # 报告大标题
PRODUCT_NAME="KLBurn"                      # 开机 banner / GRUB 菜单（只能 ASCII）
COMPANY_LOGO_FILE="logo.png"               # 放 vendor/logo.png，留空则不显示
```

也可以完全不碰这个文件，用构建期环境变量覆盖 —— 适合同一份源码出多个抬头的盘：

```bash
KLBURN_COMPANY_NAME="XX科技有限公司" sudo -E ./build/build-iso.sh
```

> ⚠️ **屏幕上那个 ASCII 大字目前是写死的**（`lib/ui.sh` 的 `_BRAND_ART`，拼出来
> 就是 "KLBurn"），改 `PRODUCT_NAME` 不会跟着变 —— 它管的是开机 banner 下面那行、
> GRUB 菜单项、`.disk/info`，以及矮屏上退化成一行时的那个名字。
> 大字下面那句说明（`BRAND_TAGLINE`，默认 `Server Factory Burn-in Test`）同理，
> 现在只能改代码。**要换成别家的名字，这两处得手工改。**
> 报告那边不受影响：`report.html` 里没有任何写死的公司名。

## 改了脚本怎么重新出盘

改 `rootfs/opt/klburn/` 下的任何脚本后：

```bash
sudo ./build/build-iso.sh
```

不需要 `--clean`。构建脚本会复用已解包的 ISO 目录树和根文件系统，
只重新执行 chroot 定制、重压 squashfs、重打包 ISO，大约 5~8 分钟。

**⚠️ Rufus DD 写盘会覆盖整根 U 盘，包括第二分区里已有的报告。**
重新写盘前记得先把 `out\` 文件夹拷出来。（用 Ventoy 方案则没这个问题。）

### 只改了报告样式？

两个报告生成器都可以脱离 U 盘单独调试，拿一份已有的报告目录重新生成：

```bash
python3 rootfs/opt/klburn/report/generate_report.py   --run-dir /path/to/20260731_101500_...
python3 rootfs/opt/klburn/report/generate_internal.py --run-dir /path/to/20260731_101500_...
```

改完跑一遍 `./tests/test-report-render.sh` 和 `./tests/test-internal-report.sh`，
它们会造一份假的 run-dir 走完整个渲染并做断言。

## 故障排查

### 构建阶段

| 现象 | 原因 / 处理 |
|---|---|
| `WORK_DIR=... 位于 Windows 挂载盘上` | 构建目录被设到 `/mnt/c` 了。`export KLBURN_WORK=$HOME/klburn-build` 后重跑 |
| `合并后的根文件系统里没有 /lib/modules` | 层裁剪配错了，把 `installer.generic` 层也排除掉了。检查 `build/config.sh` 的 `LAYER_EXCLUDE_PATTERNS` |
| apt 装包失败 | WSL 没网，或镜像挂了。换 `build/config.sh` 里的 `APT_MIRROR` |
| 构建中断后残留挂载点 | 脚本有 EXIT trap 会自动清理。真残留了：`sudo umount -l ~/klburn-build/rootfs/{dev/pts,dev,proc,sys,run}` |

### 启动阶段

**BIOS 里看不到 U 盘** → 见 `docs/usb-rufus.md` 常见问题

**启动卡住看不到原因** → GRUB 菜单按 `e`，删掉 `quiet`，`F10` 启动

**进了系统但没自动跑测试** → `Alt+F2` 登录（root 免密）：

```bash
systemctl status klburn.service
journalctl -u klburn.service -b --no-pager
```

### 测试阶段

**报告写到了 /tmp** —— 数据分区没认出来。`Alt+F2` 后 `lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINT`
确认 U 盘第二分区是 exFAT、卷标 `KLBURN`。

**硬盘测试一直被跳过** —— 看屏幕上列出的排除原因。最常见的是盘上有分区被自动挂载了，
这种情况下脚本会主动避开，属于预期行为。

**报告里的时间不对** —— 开机后会先尝试联网校时。没接网线 / 连不上时间服务器时
只能退回 BIOS 的 RTC。ISO 的时区已设为 `Asia/Shanghai`；如果差了整 8 小时，
说明这台机器的 RTC 存的是本地时间，去 BIOS 里把时间改成 UTC 即可。

**阵列卡这项是 SKIP，只有型号没有固件版本** —— 这张盘里没带对得上的管理工具。
这类工具都是各家的闭源二进制，不在 Ubuntu 源里，只能手工下载后放进 `vendor/`
再重新出盘：Broadcom/LSI 用 `storcli64`、Dell PERC 用 `perccli64`、
HPE Smart Array 用 `ssacli`、IT 模式的 HBA 用 `sas3ircu`。
步骤见 [`vendor/README.md`](vendor/README.md)。
**阵列卡始终只采集不压测**，所以这一项永远不会是 FAIL。

**显卡这项是 SKIP，说"驱动与显卡不匹配"** —— 这张盘里的 NVIDIA 驱动版本不支持
这张卡（通常是卡比驱动新）。换更新的驱动放进 `vendor/nvidia/` 重新出盘即可。
内部工程报告里有内核打出的原话和具体的 PCI ID。

**没有温度数据** —— 服务器 CPU 的温度驱动可能不是 `coretemp`/`k10temp`。
报告里的 CPU 曲线会是空的，但不影响判定，IPMI 传感器读数仍然有采集。
